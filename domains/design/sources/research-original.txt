# 设计如何帮助人理解信息、作出选择和完成行动：一套可复用、可组合、可检验的“设计与交互原语”

## 执行摘要

本研究把“设计”理解为一种**改变信息、选择与反馈的外部结构，从而改变人如何理解、判断与行动**的工作，而不是把它缩减为视觉美化、组件选择或减少点击数。对于第一次访问、背景知识有限的读者，最重要的不是让页面“更简单”，而是让五个问题更容易被回答：**这里能帮我得到什么、我现在在哪里、眼前哪些东西能操作、操作后会发生什么、接下来可以做什么。** 这五个问题分别受信息线索、视觉分组、工作记忆、既有心智模型、反馈与可恢复性等机制影响，但这些机制不能直接充当设计动作；它们需要先转译成更低一层、可执行和可验证的“原语”。Norman 对 signifier 的论述尤其适合作为这一层转换的起点：人需要的是能告诉自己“这里是什么、正在发生什么、有哪些行动可能”的可感知线索，而不是设计者心里认为某个元素“应该显而易见”。citeturn625710search0turn350879search1

本研究建议第一版只保留 **10 个设计与交互原语**：**交代页面承诺、标明位置与进度、预告入口结果、接通下一步、前置必要条件、按共同维度比较、把抽象关系外化、让变化可见、保留恢复路径、按需展开次要复杂度**。它们比“降低认知负担”“保持一致”“给用户控制感”等原则更接近可调用动作，又比“加 breadcrumb”“用 accordion”“增加按钮”更抽象，因此可以跨播客地图、课程、DIY 教程迁移。Alexander 对模式语言的定义也支持这种层级：模式是“反复出现的问题中的可复用解法”，并且彼此可以组合形成语言；它不是某个具体 UI 控件。citeturn625710search1turn625710search5

现场复核显示，**播客地图当前版本已经修复了若干旧审阅中的问题，但仍存在路径职责重复与循环**。首页现在明确写出“第一次来，先从这里开始”，并把入口指向“AI 除了聊天，还能帮我做什么？”；该问题页明确解释 Agent、提供具体例子、指向 EP18，并在页面末尾提供“AI 工具这么多，我该从哪个开始？”作为下一步。citeturn955113view0turn399337view0 “第一次用 Agent”正式路线现在也已经显示“第 1 步”、5 期总量、约 143 分钟以及显式“准备好了，再看下一步”，因此旧审阅中“路线缺少当前步数和明确下一步”的判断**至少对这一当前页面已经不成立**。citeturn399337view2 但如果读者从问题页点击“先看看这期讲什么”进入 EP18，EP18 页面当前只把“相关问题”重新指回刚才的 Agent 问题，没有把“选工具”直接接成后续动作，所以“问题页—节目页互相重复并形成回环”的旧判断仍得到当前静态页面支持。citeturn169999view0turn399337view0

DIY 站当前版本也比旧审阅所描述的状态更清楚：主页公开写明项目可以尚未完成，但不能把未测试步骤写成成功；HachimoDock 首页标明“准备中，尚未采购和实物验证”，并解释旧 13 章只是深入说明、当前标准任务顺序以双视图为准。citeturn955113view3turn399337view3 因此“12 关/13 章口径混乱”“作者设备等于通用要求”等旧问题在当前 HachimoDock 页面上已经得到明显修正；但首页仍同时承诺“新手真正能跟着完成”，旗舰项目却处于“准备中·未验证”，这形成新的**承诺—状态张力**：不是事实错误，而是首次访问者可能把“教程可跟做”理解成“关键步骤已经实物验证”。citeturn955113view3turn399337view3

学习站无法完成同等程度复核。当前抓取得到的 HTML 只有“Interactive Learning Lab / 正在载入 · 请稍候”，站点依赖客户端加载；本次研究环境不能可靠执行其中交互，因此此前关于“课程首页进入配置文件、实验入口进入 YAML、复选框不可操作、下一章未开放”等问题只能标记为**既往浏览器走查、当前未复核**，不能当成新的独立验证。citeturn955113view2 本报告也没有真实用户观察，因此所有关于“新手可能怎样理解”的判断均标记为设计推断，不能替代用户测试。

几条常见断言需要明确修正。**“点击越少越容易”没有一般性证据**：三点击规则本身没有数据基础；信息觅食理论和导航研究更关注每个候选入口是否提供足够的价值线索，而 GOV.UK 的复杂服务经验甚至经常从“一页一件事”开始，只要每一步容易回答且与整体任务明显相关，增加页面数未必是主要问题。citeturn572945search9turn589359search1turn589359search5turn589359search7 **“每页只能一个主动作”也只能是特定流程中的起始策略，而不是内容网站定律**；比较任务可能必须同时看到多个选择，路线页也应允许跳听。Apple 的当前 HIG 明确同时强调 simplicity 与 agency：界面应聚焦，却也应允许自由探索，并让引导流程可以跳过或退出。citeturn625710search2 **“所有细节都应折叠”同样不成立**：渐进披露只有在“主要信息与次要信息划分正确、进入第二层的入口明显且标签可预测”时才有收益；如果前提条件、风险、价格差异或比较维度被折叠，反而会增加错误。citeturn714156search1 **“所有内容适合卡片或图谱”也没有依据**：图形只有在空间关系、模式或比较可以因此变得更显式时才有优势；连续论证、条件说明、叙事和精确步骤通常仍需要文字。citeturn667437search1turn667437search7

最重要的系统性结论是：**应减少的是与目标无关的界面负担，不是所有认知投入。** Sweller 的经典研究针对学习与问题求解指出，有限认知资源若被与学习目标无关的处理占用，会妨碍模式获得；Chandler 与 Sweller 的分离注意实验进一步显示，需要读者自己在相隔信息间来回寻找和心理整合时，会产生额外负担。citeturn572945search0turn572945search3 但学习抽象概念、比较替代方案、判断采购风险、复述节目观点本来就需要思考。设计不应把这些“有价值的困难”消掉，而应消掉诸如猜链接去向、记住上一页的参数、辨认“展开”到底是展开还是跳页、在错误之后重填全部内容之类的额外工作。Cowan 关于短时记忆容量的综述也不能被机械转译成“界面永远只能有四项”；他的结论明确依赖控制复述、分块和长期记忆等边界条件。citeturn667437search0

## 研究框架、机制与证据边界

研究中建议把六个层次严格分开。这样可以避免把“工作记忆有限”“降低认知负担”“显示当前位置”“加 breadcrumb”写在同一个清单里。这个层级是本研究的综合提炼，不是某一文献的原始分类；其中“模式语言”继承 Alexander 的组合思想，“signifier、conceptual model、feedback”主要受 Norman、Shneiderman 与现行 HIG 启发。citeturn625710search0turn625710search1turn350879search37turn625710search2

| 层级 | 回答的问题 | 例子 | 是否直接调用 |
|---|---|---|---|
| 认知机制 | 为什么会难？ | 工作记忆有限、注意被竞争线索分散、识别比无提示回忆容易、心智模型与系统不匹配 | 否 |
| 设计原则 | 希望总体上成立什么？ | 清晰、控制感、一致性、减少无关负担 | 否 |
| 启发式 | 审阅时先查什么？ | 用户是否知道自己在哪？链接是否可预测？是否能恢复？ | 用于诊断 |
| **原语** | 遇到一种困难时可以做什么改变？ | “把入口后的结果写进入口文案” | **是** |
| 模式 | 多个原语在反复情境中的组合 | 新手路线、采购门禁、比较决策页 | 是，但较高层 |
| 组件 | 最终怎样实现？ | breadcrumb、stepper、button、details、table | 否；可以替换 |

八个核心研究问题可以由上述框架统一解释。读者判断“这里能帮我做什么”主要依赖标题、开头说明及既有经验形成的**信息线索和概念模型**；判断“我在哪”依赖页面标题、导航、路径与进度；判断“能做什么”依赖 signifier 与熟悉约定；预测点击结果依赖 information scent；判断“发生了什么”依赖及时状态反馈；“下一步是什么”则需要任务结构和当前状态共同给出。WCAG 2.2 将“帮助用户导航、查找内容并确定自己在哪里”直接作为 Navigable 指南目标，并要求页面标题描述主题或目的、链接目的可以从文字与上下文确定、键盘焦点顺序保持意义和可操作性。citeturn268513view1

注意与视觉分组尤其影响“哪些东西被认为属于一起”。Palmer 的“共同区域”研究显示，把元素放在同一有界区域本身可以成为强分组线索，并能压过接近性、相似性等其他线索；因此卡片边框、背景块和留白不是装饰性的，它们可能改变用户对信息关系的判断。citeturn572945search4turn572945search7 这同时说明“所有东西都做成卡片”是危险的：共同区域会传递“这些东西属于一个单位”的语义，如果每一块都用相同容器包裹，真正的层级和关系反而可能消失。这个结论是从感知研究向页面设计作出的推论，而不是 Palmer 直接研究网站卡片的结果。citeturn572945search4

识别与回忆的差异适用于选项、历史状态、错误恢复和跨页比较。NN/g 的说明把其机制解释为：识别任务提供更多检索线索，而无提示回忆要求人从较少线索中主动取回信息；这是专家综述而不是本研究针对中文网站的新实验，因此只能作为一般机制依据。citeturn714156search0 对本项目更安全的落地方式不是“所有输入都变成菜单”，而是：**当用户必须比较、恢复或继续时，把刚刚需要记忆的信息重新展示出来。**

心智模型应当作为解释框架使用，而不是万能因果变量。Norman 长期主张复杂系统应表现出连贯 conceptual model，使用户能够形成可预测的内部模型；但关于“明确教授概念模型是否总能提高新手表现”的实验文献并不像设计教科书口吻那么确定，早期训练研究本身就指出直接经验证据有限。citeturn350879search1turn350879search2 因此本研究不建立“心智模型对齐”这一无法直接操作的大原语，而把它拆成“入口结果可预测”“状态变化可见”“同类行为一致”等可观察动作。

反馈、控制感与错误恢复的证据类型则主要是 HCI 原理与正式规范，而非单一心理学实验。Shneiderman 对直接操作的经典描述强调对象持续可见、动作快速而增量、反馈迅速且操作可逆；Apple 当前 HIG 把 agency 明确表述为让人自由行动、持续知道发生什么，并容易从错误中恢复。citeturn350879search37turn625710search2 对涉及输入的界面，WCAG 2.2 要求自动发现的输入错误必须被明确指出并以文字描述；GOV.UK 的错误模式进一步要求保留用户原来的答案、同时在页首和字段旁指出错误，这属于成熟产品团队的规范性经验，而不是普适实验定律。citeturn819133view3turn714156search4turn714156search5

不同信息形式没有统一优胜者，应该按任务中的“需要看见什么关系”选择：

| 任务 | 优先形式 | 选择条件 | 主要代价 |
|---|---|---|---|
| 连续解释、论证、叙事 | 连续文字 | 顺序和因果要靠语句完整展开 | 扫描慢；长段落难定位 |
| 解释陌生抽象概念 | 短例子 + 简短定义 | 读者缺少既有模式，需要具体情境建立入口 | 例子可能被误当成完整定义 |
| 枚举独立项目 | 列表 | 项目同层、无复杂交叉关系 | 不适合精细比较 |
| 选择方案 | 比较表 | 存在共同维度，需要横向查差异 | 手机阅读和无障碍需额外处理 |
| 必须按先后完成 | 步骤 | 顺序本身影响结果或安全 | 容易把本可自由探索的任务强制线性化 |
| 理解结构或依赖 | 关系图 | 空间化后能显式呈现关系 | 图本身可能成为新的解码任务 |
| 判断数值趋势 | 趋势图 | 变化形态比精确单值更重要 | 精确数值通常需表格/标签补充 |
| 学习“操作—结果”关系 | 交互演示 | 可立即反馈、可恢复，操作本身是学习对象 | 工程、键盘、屏幕阅读器成本高 |
| 已知自己要找什么 | 搜索 | 内容规模大、术语可表达 | 新手不知道关键词时帮助有限 |
| 少数人偶尔需要的复杂细节 | 按需展开 | 主内容独立可理解、次要信息有明确标签 | 错误折叠会隐藏关键前提 |

图形并不因为“视觉化”天然优于文字。Larkin 与 Simon 的分析指出，图解的优势来自某些关系在空间表示中被显式化、减少搜索或推理步骤；Cleveland 与 McGill 的图形知觉实验则说明不同视觉编码对数量判断精度不同。citeturn667437search1turn667437search7 这两项工作都不能直接证明“知识地图应使用关系图”，只能给出判断条件：**当读者真正需要同时看到关系、邻近和路径时，图才可能节省推理；如果目标只是读懂一个问题，文字通常更直接。**

## 精简设计与交互原语

原语采用用户给出的工作定义：**“针对一种可描述的理解或操作困难，通过改变信息、选择或反馈的呈现方式，预期带来可观察改善的可复用动作。”** 判断一个候选是否合格可以用三个测试：如果它只能说“更清晰、更简单、更一致”，它**太宽**；如果它只能说“加一个绿色按钮、使用 accordion”，它**太具体**；如果两个候选在同一种困难上做同一种改变、得到同一种可观察结果，它们应当**合并**。这一判断框架是本研究的综合提炼。

| 原语 | 遇到的困难 | 可调用动作 | 首要检查结果 |
|---|---|---|---|
| **交代页面承诺** | 不知道这里值不值得读 | 在首屏说明“这页能帮你回答/完成什么” | 新手能用自己的话说出页面用途 |
| **标明位置与进度** | 不知道在哪、还剩多少 | 显示页面类型、所在路线和当前阶段 | 离开导航也能说明当前位置 |
| **预告入口结果** | 链接相似但去向不同 | 让入口文案说明目的地和得到的内容 | 点击前能合理预测下一页 |
| **接通下一步** | 看完不知道怎么继续 | 在完成当前任务后给出一条可完成的后继动作，同时保留退出 | 能说出“现在可以做什么” |
| **前置必要条件** | 做到一半才发现缺设备/权限/风险条件 | 在不可逆行动之前展示资格、依赖和门禁 | 不会先付款/操作再发现条件不满足 |
| **按共同维度比较** | 多个选择只能靠记忆来回比较 | 把真正影响决定的共同维度并列呈现 | 能指出为何选择 A 而不是 B |
| **把抽象关系外化** | 关系都藏在段落或记忆里 | 用例子、局部图、连接线或相邻呈现把关系显式化 | 能正确复述关键关系 |
| **让变化可见** | 操作后不知道是否成功 | 让新状态、结果或影响立即可观察 | 不需重复点击确认系统是否响应 |
| **保留恢复路径** | 犯错后怕继续探索 | 保留输入、返回、撤销或明确修复方式 | 错误后能继续而非重做 |
| **按需展开次要复杂度** | 新手被少用细节淹没 | 保留主路径所需信息，其余以清楚标签按需提供 | 初始视图足够完成主任务，且隐藏内容可被正确预测 |

这十项不是彼此独立的“十条戒律”。实际设计通常需要组合。例如“新手选择 Agent”可以组合**交代页面承诺 + 按共同维度比较 + 预告入口结果**；DIY 采购流程则通常组合**前置必要条件 + 标明进度 + 让变化可见 + 保留恢复路径**。Alexander 的模式语言本身就强调模式相互调用；因此原语体系的价值应当来自组合，而不是让人填十列检查表。citeturn625710search1

其中最值得优先落地的是以下四张完整卡片。

**卡片：预告入口结果。** 适用于“入口外观相似、但可能去节目页、问题页、外站音频、路线或关系图”的场景。改变方式不是给链接加更多装饰，而是让**动作词 + 对象 + 结果类型**在点击前可知，例如把模糊的“看看更多”分别写成“先看本期要点（站内摘要）”“在小宇宙听完整节目（28 分钟，新窗口）”“继续：怎样选一个 Agent 工具”。预期差别是读者在点击前能预测页面类型，错误进入后立即返回的次数减少。其依据主要是 information scent、WCAG 链接目的规范和 Norman 的 signifier，是综合提炼而非原文命名。citeturn572945search9turn589359search8turn268513view1turn625710search0 不适用于目的地本身有意未知的探索型叙事；也不要为了“解释清楚”把每个链接写成一段话。实现检查：脱离卡片背景只读链接，是否仍能判断去向；键盘焦点时是否仍有同样信息；可视文字应与可访问名称一致，WCAG 2.5.3 对这点有明确要求。citeturn268513view0 真实读者检查：在不允许点击的情况下问“你觉得这三个入口分别会发生什么”，记录预测与实际是否一致，而不是问“这个文案清楚吗”。

**卡片：接通当前可完成的下一步。** 适用于读者已经理解当前信息，却必须自己猜“接下来去哪里”的页面。动作是：先确定这页真正完成的状态，再提供**最邻近且当前能够完成**的一步，并同时允许结束、返回或自由探索。Apple 对 agency 的要求意味着“下一步”不应变成不可退出的隧道；GOV.UK 的分步经验则说明流程拆分可以有效，只要每一页都与总目标明显相关。citeturn625710search2turn589359search5 预期差别不是“点击率更高”，而是读者能在结束当前页时说出“我已经知道 X；如果继续，我要做 Y”。不适用于开放探索页面、参考手册和没有自然顺序的内容；这类页面需要候选方向而非伪造一个唯一“下一步”。在播客地图中，Agent 问题页已经做到“知道能做什么之后，再按自己的任务选一个容易上手的入口”；但进入 EP18 摘要页后，这个后继关系消失，当前唯一“相关问题”又回到 Agent 基础问题，因此路径可继续接通。citeturn399337view0turn169999view0

**卡片：前置必要条件。** 适用于 DIY、课程实验、账户权限、设备或不可逆决定。动作不是把全部技术细节提前，而是把**会改变“现在能不能做”这一判断的条件**放到行动之前，包括硬件、版本、费用、风险、是否已验证。DIY 站当前 HachimoDock 已经很好地使用这一原语：页面先标“准备中、尚未采购和实物验证”，并在付款前列出芯片、排线、PCB 三类红灯，而且路线明确把前几步安排为“不花钱”的检查。citeturn399337view3 预期差别是用户不会在实施中途才发现自己走错设备路线，也更容易区分“预计”和“已验证”。代价是首屏可能变长，因此应区分**决定是否开始所必需的条件**和**以后才需要的技术细节**；后者可以按需展开。真实读者检查应该给一个与作者设备不同的情境，例如“Windows、没有 3D 打印机、第一次焊接”，让参与者指出现在是否可以开始、第一笔钱什么时候应该花。

**卡片：让变化可见。** 适用于复选、实验运行、筛选、保存、提交、加载、AI 执行等操作。改变是让用户能从界面直接观察“动作已经被接收、现在处于什么状态、下一步依据是什么”，而不是只让控件本身动一下。Shneiderman 的直接操作模型和 Apple HIG 都把快速反馈与保持控制作为核心特征；错误情况下 WCAG 还要求把被检测出的错误清楚标出并用文字说明。citeturn350879search37turn625710search2turn819133view3 对学习实验尤其重要：如果结果只是输出两张长表，“程序运行成功”不等于“学习目标的差异已经可见”。可以在表前增加一句针对目标的结果摘要、标注真正变化的列，并保留原始表给需要核对的人；这里的目标不是替学习者得出所有结论，而是让**本次操作造成的状态变化容易定位**。这一具体学习站应用仍属设计提案，因为当前交互未复核。citeturn955113view2

原语之间存在真实冲突，因此调用时必须记录“为什么这次选它”。**简洁 vs 解释充分**：先删与当前判断无关的说明，而不是删风险和前提；**引导 vs 探索**：把“推荐下一步”写成推荐，不锁死全站路线；**一致性 vs 情境适配**：保持相同角色与行为的一致，而不强迫不同任务拥有同一页面结构；**氛围 vs 可读性**：安静海景可以保留，但文字对比、焦点、目标尺寸与键盘顺序需要独立验收。WCAG 2.2 要求全部功能可通过键盘操作、焦点可见且不被作者内容完全遮挡；其 AA 最小指针目标为 24×24 CSS px，并允许特定例外。citeturn819133view0turn819133view1turn268513view0

## 现场复核与样板路径提案

本次现场核对分成四种证据状态。**静态内容核对**是 web 抓取得到的当前 HTML；**工具化链接跟随**是本研究实际从当前页面跟随可识别链接打开目标页；它可以确认某个链接在抓取环境中有目的地，但不是完整浏览器点击测试。**AI 设计推断**是根据页面结构预测新手可能发生的理解问题；它必须在真实测试中验证。**真实用户观察**本次为零。学习站既往浏览器走查属于用户提供的历史材料，本次没有独立重现。这个区别应继续保留到未来原语数据库里，避免同一观察被转述多次后看起来像“多次验证”。

当前主路径可以表示为：

```mermaid
flowchart LR
    A["首页<br/>承诺：从一个听得懂的问题开始"] -->|从这里开始| B["Agent 问题页<br/>回答：AI 除聊天还能做什么"]
    B -->|先看看这期讲什么| C["EP18 摘要页<br/>节目证据与时间轴"]
    B -->|想再了解一步| D["工具选择问题页<br/>按任务选择入口"]
    C -->|相关问题| B
    C -. 建议新增 .->|继续：选一个 Agent 工具| D
    D --> E["EP38 / 后续问题"]
```

首页当前承担的是**建立站点承诺和第一次访问入口**。它说“让 AI 真正帮上你的忙”“从一个听得懂的问题开始”，并明确标记“第一次来，先从这里开始”，这是很强的入口信息线索，应该保留。citeturn955113view0 建议不再给这一块增加更多说明，因为当前首屏已经足够回答“这个站能帮我做什么”。

Agent 问题页承担的任务应定义成**让第一次接触 Agent 的读者得到一个最小概念模型，并决定是否需要完整节目**。当前页面已经有定义、编辑构造例子、EP18、依据时间点和下一问题，层次基本成立。citeturn399337view0 可以进一步让两个动作角色更加明确：

```text
完整理解这一期
[先看 EP18 的要点与时间轴]   站内摘要 · 约 2 分钟
[在小宇宙听完整节目]          28 分钟 · 外部链接

如果已经理解 Agent 能做什么
[继续：怎样按自己的任务选一个工具 →]
```

这样调用的是“预告入口结果”和“接通下一步”，不是新增页面。

EP18 页面承担的任务不应再次完整承担“Agent 是什么”的教学页职责，而应承担**节目层证据**：本期主题、经核实的时间轴、节目来源以及“听还是不听”的判断。目前它重新出现同一个问题、相同例子和同一答案，因此内容职责与问题页重叠。当前可核实的节目内容只有页面公开的几点：03:56 的 Agent 形态演进、12:03 的长期记忆讨论、22:30 的 SuperPower/设计讨论；站点也明确说明这些时间轴摘自节目原说明、未逐秒复听校准，因此本报告不把它们进一步扩写成节目独有观点。citeturn169999view0 更合适的层级可以是：

```text
EP18 · 28 分钟
这一期适合谁：
想理解“聊天工具”和“能持续执行任务的 Agent”差别的人。

听前先知道：
03:56  工具形态演进
12:03  长期记忆
22:30  从执行走向设计
〔以上为官方节目说明中的时间轴，未逐秒校准〕

[听完整节目]
[继续：我该从哪个 Agent 工具开始？ →]

依据与编辑说明
……
```

这样问题页负责**解释**，节目页负责**证据与节目选择**，下一步负责**行动推进**，三种页面不再互相复制。

“备课 → EP47”提供了很好的对照。当前首页的“材料很多，怎样让 AI 做出一份能讲的课？”直接以“看这期的回答”进入 EP47，而 EP47 又把相关问题链接到教学问题页。citeturn955113view0turn399337view1 教学问题页则再链接回 EP47，并把下一步设为“AI 整理得很好，我为什么还是没学会？”citeturn169999view1 这说明站点目前存在两种方向：**问题→节目**与**节目→问题**。两者都可以存在，但第一次访问者需要从入口文案看出差异。建议首页的生活化问题统一去“问题页”，而“最近一期/全部节目”统一去“节目页”；这样页面类型与入口语义稳定。若不想改信息架构，最低成本做法是把首页 CTA 改成“先看问题解答”或“直接看 EP47 节目页”，明确是哪一种。

正式路线则是目前最清楚的模式实例。“第一次用 Agent，从哪听起”现在显示“第 1 步”、5 期列表、总时长和“准备好了，再看下一步”，同时允许“可按需要跳听”。citeturn399337view2 这很好地解决了“引导与自由”的冲突：它提供推荐顺序，但不把推荐伪装成必经流程。可以把这一结构反向提炼成一个“学习路线模式”：**当前位置 + 本步目的 + 当前内容 + 推荐下一步 + 完整路线 + 可跳过声明**。

DIY 的迁移检验表明“前置必要条件”和“状态可见”是跨域原语。当前首页明确展示项目状态，“准备中 · 未验证”“已完成 · 待整理教程”等，并说明状态不等于完成保证；HachimoDock 又更明确地写出当前没有采购和实物验证。citeturn955113view3turn399337view3 但入口文案仍可以更精确。当前“人类制作版（推荐）”“先跟着做”容易被理解为已经存在端到端实物验证。建议按真实状态改为：

```text
当前状态：准备中 · 尚无完整实物验证

没有设备也可以现在开始
[先完成 1–4：资料、兼容与数字模拟]
不会产生采购支出

等这些门禁通过后
[进入采购与实物制作]
当前步骤将随真实验收逐步更新
```

这不需要把项目隐藏到“完成后才发布”，反而保留了当前站点很有价值的透明实验日志风格。citeturn399337view3

学习站的迁移只能形成待验证设计假设。若此前“实验运行后输出两张长表”的观察仍成立，可应用“让变化可见”：不是删除原表，而是在原表前添加“本实验要观察什么”“哪两列/哪两行发生了关键变化”，再让读者自己写一句解释。如果“完成复选框不可操作”的历史问题仍存在，则首先是 signifier 与实际行为失配：看起来像可操作控件就必须能操作，或者应改成静态状态标记。Norman 对 signifier 的论述正好解释这种失败机制，但当前站点只抓到 loading shell，因此这些必须标注**待实际浏览器复核**。citeturn625710search0turn955113view2

作为外部对照，GOV.UK 的表单结构说明很适合检验“点击越少越容易”和“每页一个动作”的边界。它建议复杂公共服务从“一页一件事”开始，并明确说用户研究可以告诉团队何时合并页面；政府团队后续经验也记录到，只要每个问题容易回答且明显服务于整体任务，参与者对额外翻页本身通常并不特别在意。citeturn589359search5turn589359search7 因而可迁移的不是“每页只能一个问题”，而是更抽象的原语：**当多个决策相互干扰时，把当前必须完成的判断单独呈现；当比较依赖同时查看多个值时，再把它们合并到同一视图。**

## 与人生、写作系统的兼容方式

这套体系不宜把 Goal、State、Observation、Claim、Decision、Activity 重新复制一遍。更合适的做法是：**共享可追溯的方法，不强求共享领域对象。** 现有正式文件尚未提供，因此以下兼容设计标记为**待核对**；未来若正式定义与此处冲突，应以正式文件为准。

**直接共享的部分**是证据和修订基础设施。设计原语与人生/写作系统都可以共享：唯一 ID、来源、支持/反驳关系、版本、修改原因、状态、案例、真实验证记录。Evidence 可以继续表达某个 Observation、Claim 或设计判断受到什么支持或反驳；“材料—新解释—成稿”的来源追溯思想也可以直接迁移为**现场材料 → 设计解释 → 原语调用 → 修改方案 → 用户观察**。这种共享是数据治理层面的，不要求“一个页面”也变成人生系统中的 State。

**可以类比、但不要合并的部分**包括 Goal、Observation、Decision、Activity。一次设计工作当然有 Goal，例如“第一次访问者能找到第一期节目”；也会有 Observation，例如“EP18 页面只把相关问题链接回 Agent 基础问题”；Decision 可以记录“在节目页新增选工具下一步”；Activity 可以记录“修改 CTA”。但这些只是把现有通用工作对象用于管理设计工作，不意味着“设计原语 = Activity”或所有产品对象必须被强制塞进这六类。当前站点本身已经有 page、episode、question、route、project、chapter、experiment 等领域对象，保留它们更自然。citeturn955113view0turn399337view2turn399337view3

**应保持领域独立的部分**包括 WCAG 合规状态、键盘顺序、焦点行为、交互状态机、响应式布局、组件语义以及站点信息架构。这些不是人生/写作原语的类比对象，而是 Web 设计自身的约束。WCAG 2.2 对键盘操作、焦点、链接目的、错误识别和目标尺寸都有规范性要求，因此不能仅通过“原语卡片觉得合理”来替代测试。citeturn819133view0turn268513view0turn268513view1turn819133view3

推荐的后台记录结构尽量轻：

```text
Primitive
  id
  name
  problem
  action
  expected_observable_change
  boundaries
  evidence_refs[]
  cases[]
  version

PrimitiveUse
  primitive_id
  target_page_or_flow

```

其中至少把三种状态拆开，不能只有一个“已验证”：

```text
  cited / source-checked / source-limited

  untested / observed / contradicted / mixed
```

这与当前 DIY 站把 `planning / preparing / building / verified / completed-unwritten / archived` 分开的做法在精神上相近：文档写完不等于实物通过。citeturn399337view4 但两套状态不应直接共享枚举；DIY 的 `verified` 是项目事实状态，而原语的 user validation 是设计观察状态。

给人或 Agent 调用时，不建议先问“这里能套哪些原则”，而建议按具体问题调用：

```text
我不知道这一页是干什么的
→ 交代页面承诺

两个入口看起来一样，但去不同地方
→ 预告入口结果

我必须记住上一页的数据才能选
→ 按共同维度比较 / 让选择可识别

我完成了这页却不知道去哪
→ 接通下一步

操作后不知道有没有生效
→ 让变化可见

做到中途才发现缺设备或权限
→ 前置必要条件

页面看起来太复杂
→ 先区分哪些信息是当前行动必要条件；
   只有真正次要的信息才调用“按需展开”
```

这比让设计者填写“注意、工作记忆、心智模型、认知负荷”分类表更适合日常工作；认知机制保留在卡片背后的解释和证据里。

## 验证计划、暂缓候选与来源附录

第一轮真实新手验证的目的不应是证明“新设计有效”，而是找出**原语预测是否与真实行为相符**。建议做两轮小规模质性测试，每轮招募背景知识有限但真实可能使用这些内容的人，覆盖至少桌面键鼠、手机触控以及一部分键盘操作场景；无障碍合规另外做 WCAG 技术检查。人数不用于产生人口比例结论，因此不要写“80% 用户成功”之类的小样本百分比。每名参与者保留独立记录，第二轮只在第一轮修改后再运行。

核心任务可以固定为四组。播客地图任务：“你第一次听说 Agent，找到适合你的起点；看完后告诉我下一步准备做什么。”备课任务：“你有很多材料，找到一个能帮助你组织课程的内容，并告诉我为什么选它。”学习站任务：“完成一个最短实验，并告诉我操作前你预期会变化什么、运行后你实际看到了什么。”DIY 任务：“你没有打印机、没焊接经验，现在想做 HachimoDock；判断今天可以做什么、什么时候才应该花钱。”这些任务分别覆盖理解、选择、执行、门禁和恢复。

每次任务记录五类观察，而不是只记点击率和停留时间：

| 要观察的能力 | 现场问题 | 记录方式 |
|---|---|---|
| 理解 | “这页主要能帮你解决什么？” | 原话 + 是否与页面职责一致 |
| 预测 | “点击这个以后你觉得会看到什么？” | 预测目的地，再与实际比较 |
| 选择 | “为什么选这个入口而不是另一个？” | 用户使用的线索与犹豫点 |
| 完成 | 是否无需研究员救援完成当前任务 | 完成、需提示、错误路径 |
| 恢复 | 出现误操作后怎样回到任务 | 是否发现返回/撤销/纠错方法 |
| 下一步 | “现在你认为应该做什么？” | 是否能说出可执行后继动作 |

额外记录**误操作不是为了扣分，而是为了识别模型不一致**：错误点击后是否马上意识到目的地不符；是否利用浏览器返回；返回后上下文是否丢失；是否重复点同一个入口；是否出现“我不知道这个能不能点”。对学习类内容还要加入一个理解检验，例如让参与者不用页面原句解释“Agent 和聊天工具有什么不同”，因为界面顺畅并不等于学习发生。Sweller 的研究本身也提醒我们，问题解决表现与模式获得不是同一件事。citeturn572945search0

技术验收单独执行：Tab 顺序应保持意义与操作性；所有功能均可键盘执行；焦点可见且不会被 sticky 内容完全遮挡；链接目的从可见文本及程序化上下文可判断；触控目标满足 WCAG 2.5.8 最低要求或其明确例外；自动检测错误时用文字指出；移动端 reflow 后比较表和步骤仍能理解。citeturn819133view0turn819133view1turn268513view0turn268513view1turn819133view3 WCAG 合规只能证明部分最低可访问要求，不应写成“新手已理解”或“设计已验证”。

本轮删除、合并或暂缓的候选如下：

| 候选 | 处理 | 原因 |
|---|---|---|
| “每次点击新增知识” | 删除 | 把信息获取误当成所有点击的目的；确认、继续、恢复和状态改变都可能是合理点击。信息觅食更关注每一步的价值线索，而非“新知识量”。citeturn572945search9turn589359search1 |
| “每页只能一个主动作” | 降级为模式条件 | GOV.UK 证明它可作为复杂表单起点，但比较页、导航页、开放探索页需要并列选择。citeturn589359search5turn625710search2 |
| “减少点击” | 删除为独立原语 | 点击数是成本的一部分，但不是可靠目标；高信息线索的更多步骤可优于少量但含糊的跳转。citeturn589359search1turn589359search8 |
| “降低认知负担” | 保留为解释原则，不作为原语 | 太宽，无法直接说明该改什么；还可能错误消除学习中必要思考。citeturn572945search0turn572945search3 |
| “识别优于回忆” | 暂不独立成原语 | 更适合作为“比较、位置、恢复”等原语背后的机制，否则范围过宽。citeturn714156search0 |
| “所有细节折叠” | 删除；替换为“按需展开次要复杂度” | 渐进披露要求先正确区分核心与次要信息，且入口必须可预测。citeturn714156search1 |
| “一致性” | 保留原则，不作为单独原语 | 太宽；真正可执行的是同类入口保持同类结果、同状态使用同表达。WCAG 只对部分导航和识别一致性提出规范要求。citeturn819133view4 |
| “卡片化内容” | 删除 | 卡片是组件/布局实现，且共同区域本身会表达分组语义。citeturn572945search4 |
| “知识图谱化” | 暂缓 | 只有当空间关系显式化确实减少搜索或推理时才成立；尚无本站新手证据。citeturn667437search1 |
| “审美氛围” | 保留为产品设计目标，不作为交互原语 | 它可以影响体验，但不能替代可读性、操作性和无障碍要求；Apple 也明确提醒不要让 delight 妨碍核心任务。citeturn625710search2 |

这套原语的成功标准因此不应是“卡片数量够不够”“有没有遵守所有 UX 原则”，而应是更严格也更实用的三件事：**遇到具体设计困难时，人或 Agent 能找到一个足够小的可执行改变；能够指出这个改变依据什么、在哪些条件下可能失败；上线后能够用真实读者行为决定保留、修改还是废弃它。** 这正好把设计工作从“经验判断的集合”变成一套能够持续积累 Observation、Evidence、Decision 和版本修订的实践工具。
