# 使用指南：从当前问题开始

先处理眼前要判断的事，再决定需要记录哪些对象。不要为了完整填满六个目录，把每段随想都扩写成目标、判断、决策和行动。本指南是依据既有 Life State 定义编写的使用入口；权威来源与版本边界分别见 [概念定义](CONCEPTS.md) 和 [兼容说明](COMPATIBILITY.md)。

<a id="separate"></a>
## 一段材料混在一起：拆开事实与判断

1. 找出原文或记录中的具体发生事项，保留可定位出处。有人说“我觉得 X”可以成为“某人说过这句话”的 Observation，但不能因此把 X 的内容也当成事实。
2. 把因果解释、评价、价值立场和路径判断分出来。问“哪种观察能检验它？”有具体答案，再作为 Claim 候选。
3. 只把当前可核查的状况写进 State。过去事件是 Observation；“还缺什么信息”“应当换哪条路”是判断或检验点。
4. 本人尚未承诺的建议留作候选。不要为了让记录看起来完整，推断出一个 Decision。

**检查结果**：读者能分清“发生了什么”“我如何解释”“我已经决定什么”。任何重要陈述都能回到原文或结构化记录；无法定位的出处标为待溯源。[来源：自带定义的引用纪律、边界判定优先级](sources/life-state-v2/_definitions/concept-definitions.md)。

<a id="check-claim"></a>
## 一个判断可能站不住：检查判断与证据

先把判断的原句、适用范围、论证和可检验点写清楚。检索支持与反对它的观察，核对来源是否相同；同一材料被多次总结，不能因此算成多份独立证据。

对于可证伪判断，问“什么结果会推翻它？”对于立场或偏好，问“哪些持续行为支持它，哪些行为与之背离？”不要强行给所有价值判断寻找一次即可决定一切的实验。

Life State 使用 `INCONCLUSIVE / SUPPORTED / CONTRADICTED / WEAKENED / RETIRED` 五态；新建判断默认 `INCONCLUSIVE`。状态变化应说明所依据的观察及范围。它不是旧 PCA 按边计数得出的四态，不能直接转换。[来源：Claim 定义与状态语义](sources/life-state-v2/_definitions/concept-definitions.md)、[版本差异](COMPATIBILITY.md#versions)。

**最小产出**可以只是：一条范围清楚的判断、它当前的支持与反对材料、一个还未解决的检验点。不要因为暂时没有证据就补写故事，也不要把已有判断改写成另一个更容易成立的命题。

<a id="next-action"></a>
## 已经讨论很多：把缺口变成有产出的行动

先说明这次行动要服务哪个目标或检验哪个判断，再问“做完后，会得到什么可观察的结果？”选择足够小、现在能执行的一步，并区分行动开始前的预期与事后实际产出。

Activity 的意图取自既有四类：`Observe / Hypothesize / Test / Optimize`。其中 `Test` 与 `Hypothesize` 需要关联判断。行动状态取自既有四类：`active / next / done / superseded`；原 Life State 工作流维护唯一的 `next`，不能把每个候选都标成下一步。[来源：Life State README](sources/life-state-v2/README.md)、[Activity 定义](sources/life-state-v2/_definitions/concept-definitions.md)。

调用时明确预期产出，并引用已有目标或判断。这是本指南采用的清楚表达方式；来源文件对 `expected` 字段强制程度仍有未解决的差异，不能据此宣称通过原校验器，详见 [遗留差异](COMPATIBILITY.md#open-differences)。

**检查结果**：行动结束后能写出新的 Observation、状态变化，或如实写明没有得到预期结果。“做了很多”“完成任务”本身不足以支持原判断。

## 一次整理什么时候结束

眼前的判断已说清，事实与解释能区分，后续行动或暂不行动的理由明确，就可以结束。需要本人选择而尚未选择的地方，保留候选，不把它写成已确定承诺。

只有在任务确实要求写入真实 Life State 记录时，才进入原数据环境的格式、语义和授权流程。本方法模块没有携带那些运行程序；源文件中的命令是历史环境说明，不能在当前目录直接运行后声称原系统验证通过。[来源范围](sources/README.md)。
