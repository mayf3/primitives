# Agent Workflow 候选原语

版本 **0.1.0**。以下是八个**可检索候选操作**，不是八条已证独立的公理。每项都只负责一个局部决定；可能在未来合并为组合，也可由既有服务能力承担。统一状态及不变量见 [数学模型](FORMAL_MODEL.md)。

<a id="freeze-goal"></a>
## 1. 固定原目标与验收

**职责：** 将用户委托、原验收、允许范围及显式取消权绑定成稳定目标；版本更迭不默改原意。

- **触发与输入**：业务目标开始，或者后续改版可能改变完成含义；输入含目标、原验收、已授权范围、决策主体。
- **动作与产出**：形成可引用的目标版本、验收项及其来源；无法判断的要求列为待确认输入。
- **正例**：原请求要求“得到可公开的文章并由本人审核”，不能只因审稿脚本 PASS 就闭合。
- **相邻反例**：按等待时长自行取消；或把“已提交 PR”换成“网站已发布”的验收。
- **接口**：为后续各小节点提供不变目标；真实领域判决由对应验收者承担。
- **删并假设**：可与创建义务合并，但不能隐去验收和取消权的独立身份。

<a id="scope-node"></a>
## 2. 缩小为单步工作包

**职责：** 为低能力执行者提供足够但不多余的输入，只要求一个可验证的局部输出。

- **触发与输入**：Agent 反复做巡检、解释历史或同时承担实现与验收；输入为当前 visit、明确工具、工件和验收项。
- **动作与产出**：固定本步动作、执行角色、允许的工具及成功/失败/UNKNOWN 出口；确定性判断尽量交程序。
- **正例**：开发只负责修准确测试失败并自测，独立 Tester 判断该候选是否满足固定条件。
- **相邻反例**：让 Agent 自行查全部历史、猜哪个角色有权限、同时改图又做生产验收。
- **接口**：执行前须提供合法身份与工件；本步骤产出不承担全局后继调度。
- **删并假设**：可以是通用节点合同而非独立运行角色；若每个节点天生包含相同合同，可降为模板。

<a id="bind-identity"></a>
## 3. 固定业务、流程与尝试的不同身份

**职责：** 防止结果被算到相邻任务、旧版本或错误执行轮次。

- **触发与输入**：跨系统派发、重复/迟到回执、RETURN 新 visit、失败重试。
- **动作与产出**：关联原任务、业务操作键、instance/visit/sv、attempt/generation、输入摘要与授权身份。
- **正例**：两份相同载荷的请求各有原操作键，结果只能结算它实际属于的义务。
- **相邻反例**：凭同一 actor、同时间窗或“不是旧 attempt”认领任何结果。
- **接口**：为留证、对账、合法提交提供身份，不自行授权或判断业务内容。
- **删并假设**：可编入持久化信封；但合并时不得失去三种身份的区别。

<a id="persist-obligation"></a>
## 4. 持久化可发现的责任

**职责：** 保证有一笔真实、合法且未完成的工作时，有可恢复的当前责任与接收入口。

- **触发与输入**：实例创建、节点结果形成、治理子任务成立、通知丢失或进程退出。
- **动作与产出**：持久保存义务、依赖、授权边界、合法消费者及发现/补漏途径；必要时记录重建后继的充分事实。
- **正例**：执行者退出后，另一运行中的消费者仍能从权威队列读到原待办。
- **相邻反例**：文件名叫 pending、定时器一直空扫、或报告写“已交某责任链”却无人实际消费。
- **接口**：满足 S1 的机制前提；真正接纳需要有运行时和权限证据。
- **删并假设**：可由正式工作流事务与 Outbox 承担，不要求第二 Scheduler 或第二账本。

<a id="observe-effect"></a>
## 5. 将真实效果和证据分别记账

**职责：** 区分“外部世界发生了什么”与“当前主体知道并能证明什么”。

- **触发与输入**：执行工具、外部写入、测试产生工件、响应丢失或部分失败。
- **动作与产出**：保存原始回执/工件、摘要、适用候选、观察主体及未知；不以模型自报取代权威事实。
- **正例**：Svc 可能已提交但调用方丢响应，记录效果 UNKNOWN 并保留原操作信封。
- **相邻反例**：网络 timeout 当未发生；后继已分配就当下一 Agent 已执行。
- **接口**：将观察送给核验和对账，不能从 K 的空白断言 W 未变化。
- **删并假设**：工件生成与证据核验可并为一台组件，但必须保留“事实/观测”的可检查区别。

<a id="verify-handoff"></a>
## 6. 真实验收并建立后继

**职责：** 在可信结果被消费后，按原合同准确关闭当前义务，并持久建立所有必需后继。

- **触发与输入**：本步执行结果返回，需 PASS/FAIL/治理分流或合流。
- **动作与产出**：验证身份、原标准、合法出口；在原子事务/可靠重建边界下以新义务替代旧义务。
- **正例**：测试已通过但父流程还需 security_review，先形成真实下一责任才结束测试阶段。
- **相邻反例**：仅写 nextNode 字段；CONSUMED 被汇报为 GREEN；Case RESOLVED 直接关闭原业务。
- **接口**：S1 与 S2 的交界，禁止用作者自填 PASS 降低父任务标准。
- **删并假设**：单个串行事务可以同时核验和交接，但不得出现“已完成而后继未知”的空窗。

<a id="reconcile-unknown"></a>
## 7. 对账未知效果而非盲重试

**职责：** 对已经可能产生外部效果的原操作，给出安全的恢复分支。

- **触发与输入**：响应丢失、崩溃、重试耗尽、异步结果迟到；输入必须包含准确操作键、事实所有者和可读关联。
- **动作与产出**：以原键或权威历史回读；证明已发生则复用效果；证明未发生且可排除迟到生效才安全发起；否则保留 UNKNOWN 与补证接收者。
- **正例**：原请求完成但本地未 ack，从服务端合法重放或读回原键，同一逻辑效果只发生一次。
- **相邻反例**：换新键重复写；依据“最新一条相同内容”直接标成功。
- **接口**：保持 S3，若无可信读回则承认 L2 暂不能保证。
- **删并假设**：可由业务平台的既有幂等/对账接口承担，必须在跨系统交接处显式暴露其适用边界。

<a id="govern-resume"></a>
## 8. 治理失败并返回原目标

**职责：** 使失败、材料缺失、环境异常、定义问题和合法人类等待各有持续责任，修好后回到原任务。

- **触发与输入**：同类错误反复、退回上限、守卫拒绝、执行者自身失败。
- **动作与产出**：按权威错误事实分类；建立或复用正式诊断/修复/人类输入义务；修复独立验收和合法采用后，解除原门并恢复原检查点。
- **正例**：写作退回三次后，自动生成具体修稿差异和材料校验子任务，而不是让用户再说“继续”。
- **相邻反例**：达到 3 次就一律 HUMAN_REQUIRED；修好了测试环境却不恢复测试；治理 Case 解决却宣布原业务完成。
- **接口**：可合法等待真人不可替代的选择，但不得越权代签、清 fence 或盲重放。
- **删并假设**：可分解成诊断、修复、验收、恢复多个子流程；只有存在独立持久状态、权限或恢复需求时才增加节点/角色。

## 组合而非额外的“万能 Agent”

常用组合：`freeze-goal → bind-identity → persist-obligation → scope-node → observe-effect → verify-handoff`；出现未知则接 `reconcile-unknown`，发生失败则接 `govern-resume`。顺序不是强制模板，多个动作可能由一个现有服务事务承担。

要判断是否可删除某项，固定原任务、默认能力与成本，尝试用其余方法重建同样的安全、活性和可观察区别；如果只把它藏进参数或另一个 Agent 的隐式判断，不能算成功删并。
