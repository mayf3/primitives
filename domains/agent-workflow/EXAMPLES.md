# 十一个合成反例：如何推翻过强的无人值守声明

下述 H1–H11 是从私有独立审阅的**失败类型与对照逻辑**抽出的合成案例，不包含真实实例、人员、业务内容、会话编号或私有运行回执。它们用于提出可以失败的测试，不是历史统计，也不是对实际部署的认定。对应的原语见 [PRIMITIVES.md](PRIMITIVES.md)，数学性质见 [FORMAL_MODEL.md](FORMAL_MODEL.md)。

| 代号 | 合成情形 | 能支持的有限结论 | 反例应怎样构造 |
|---|---|---|---|
| **H1 通道与效果分离** | 某次 dispatch 已送达，随后 execution 回执丢失 | 传输成功 ≠ 执行成功 | 送达后终止 worker，检查是否产生持久对账义务 |
| **H2 自然多步接续** | 第一个节点提交后，后继正常启动并最终走到图终点 | 该图有可运行自动链 | 遮掉协调催办，核每个 visit 真实入站及原 AC |
| **H3 另一个 visit 被接纳** | RETURN 后新的 visit 由同角色合法进入 | 控制流重接可用 | 使用旧 visit 的回执结新 visit，应明确拒绝 |
| **H4 同一 Agent 两种表现** | 复杂巡检只报告缺项，具体工作树任务能交代码 | 任务包、环境和能力需要区分 | 冻结模型/工具，只改变任务粒度作对照 |
| **H5 窄测绿、环境红** | 单元集全过，但完整测试依赖缺失 | 局部 PASS 与环境 FAIL 可同时真实 | 换工作区、冻结版本、按套件分别汇报 |
| **H6 合法 409** | Case 仍打开，普通推进被拒 | 守卫可能工作正确 | 是否有真实治理消费者处理 Case，恢复原任务 |
| **H7 测试自填标准** | 修复作者自行声明 PASS，独立验收无固定断言 | 自报不等于可信结果 | 删掉一项必要证据，验证验收真能失败 |
| **H8 分配但没人接** | 实例在工作列表，执行消费者只扫描另一类 activation | 分配存在不等于自动调度 | 冻结实例类别、版本、actor，验证哪个消费者读到当前责任 |
| **H9 工件消费但后继丢失** | 运行时记录 CONSUMED，下一节点从未创建 | 接收结果不足以保证责任连续 | 消费提交后、后继写入前退出，并用另一进程重新发现 |
| **H10 候选与安装版差异** | 测试工作树返回正常，安装版仍拒绝 | 候选 PASS 不代表生产有效 | 固定制品 hash、环境、入口，对两者独立实测 |
| **H11 变异检验** | 删去身份绑定或后继消费者而测试仍绿 | 现有测试漏了关键性质 | 对防串账、重启发现分别做故意破坏并要求 RED |

## 反例一：两份相邻义务，结果不能串账

同一时刻，任务 A、B 各有持久 WAIT。只有 B 产生匹配的成功工件。若消费者只按时间取第一份工件，可能先把 A 错误结清。**补齐的是义务/操作/attempt 身份关联**，不是将轮询改得更勤快。

可失败检查：B 工件只结清 B；A 保持 OPEN 并有实际接收者。若 A 无人接走，虽没有误完成，仍可能违反 S1。

## 反例二：双端退出，谁重新发现同一操作？

提交外部命令前持久保存原操作信封。服务端已提交，但客户端响应丢失；执行者和消费进程同时退出。下次由**已运行的正式恢复者**读到未确认义务，按原键对账，不能由测试脚本代提交，也不能凭数据库最近一条记录自证本次成功。

可失败检查：原操作键稳定；重启后消费者真正读取原义务；最终只有一个逻辑 RETURN；后继属于准确 visit 且实际接单。

## 反例三：反复退回、人工门与治理

文章流程的读者测试三次反馈相同的内容缺陷，当前系统为安全拒绝第 4 次 RETURN。正确行为不是直接放开 100 次重试，也不是把超限等价为“用户必须批准”。应产生具体差异诊断、材料验证或 Definition 治理义务；有权修复、独立验收后才沿合法路径恢复原任务。

若原业务真的要求真人批准发布或物理行动，持久人类门依然有效；不可替代的人类事实不得由治理 Agent 编造。

## 反例四：前置责任只有本地文件

一个试点把下一步写入 `pending-successors.json`，另一个守护进程实际只读取 `registry.waits`。两份文件都存在，定时器也一直运行，却没有任何消费者读取真实后继。这不是“模型太笨”，而是持久责任没有可执行发现入口。

可失败检查：事先关掉所有测试主进程；引入一个真实非空后继；让受管消费者自行找到它、接单、核证和继续。

## 反例五：子任务成功却不等于父任务成功

一个诊断 Case 得到 RESOLVED，一个测试脚本 65/65 GREEN，一个 safety shell 5/5 GREEN；但业务正式实例仍停在旧节点。**三项成果各有用处，却不自动证明父任务的原验收已满足。**

可失败检查：用真实正式状态、必要外部效果与原验收逐项对照；文件名叫 FINAL、测试名叫 security_review 不等于正式签核或图节点。
