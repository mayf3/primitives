# 后续评审纳入与 Lean 证明范围

**Agent Workflow 0.3.1 · 2026-11-20 · 条件定理与合成反模型**

本次把较晚评审中的不确定性、状态充分性、共同误判与条件进展要求加入公开规范，并以 Lean 4.19.0 核验其中的形式化切片。0.3.0 进一步连接证据更新与进展模型，消除逐边界真值包含的直接假设；0.3.1 加强返回合同，防止后来的合法返回掩盖先前非法返回。公开跟踪见 [Issue #3](https://github.com/mayf3/primitives/issues/3)。证明代码、复现命令和公理审计范围见 [lean/README.md](lean/README.md)。

此前 0.1.0 来自 2026-11-15 的 v1.1 概念稿，**没有完整纳入** 2026-11-18 v2.4 和 2026-11-20 后续复验。此次修订明确补上以下语义；不是对较新源稿、其大型有限检查器或真实运行证据的完整移植。原八项原语 ID 保持不变。

## 1. 状态与责任的几个补充

在 [原状态机](FORMAL_MODEL.md) 的构形之外，任何具体实现精化都必须明确：

- **真实必需责任** `Req(H)` 来自原合同与实际历史，不能定义成“本次扫描器查到的集合”。否则扫描器漏项反而让责任守恒真空成立。
- **持久事实、易失状态、实际世界**分别建模。崩溃可以删除易失信息，不能抹掉已经发送的请求、在途写入或迟到效果。仅记录当前节点不足以恢复。
- **工件身份与可用性**分别检查。正确的 hash 或路径不保证合法接收者能读到同一份原始字节；这是原 S1–S3 之外需要明确的工件交接义务。
- **历史提交合法、当前采用合法、当前仍有效**分别判断。一个历史授权回执不自动授权当前执行或采用。
- **尝试上限与原责任寿命**分别记录。换 WAIT 标签、会话或 generation 不应重置同一失败条件的累计预算，也不能取消父任务。
- **发现、接纳、执行、核验、采用**分别留下事实。候选策略存在、定时器运行或升级消息已发送，均不能替代实际采用和原目标完成。

这些是实现必须满足的规范要求；本轮 Lean 没有证明一个生产存储、扫描器或权限实现满足它们。

## 2. 不确定性：保留真实世界，而非相信报告

设 `B` 是当前合法信息仍允许的世界集合，`Step` 是可能转移，`Emits` 是环境可能产生的观测关系。更新为：

$$
B'_{a,o}=\{w'\mid\exists w\in B:\operatorname{Step}(w,a,w')\land\operatorname{Emits}(w',o)\}.
$$

`Emits` 可以包含错误、相关或蓄意诱导的报告。若报告不可信，收到“已生效”不能自动排除“未生效”的世界。证明不要求 `B` 单调缩小或最终变成单点；一个合法的原键幂等操作也可以让多个可能世界汇合到同一个安全结果。

Lean 已证明：**初始信息集含真实世界，且声明关系覆盖实际转移和观测，则任意有限观测轨迹后，真实世界仍在信息集中。**见 `update_contains_actual`、`trace_contains_actual`。两个具体定理让同一条“已生效”报告同时保留 `absent` 与 `applied`。

这不是“估计器总能知道真相”。把假报告排除在 `Emits` 之外，会让真实轨迹不满足模型覆盖前提；证明工具不能替作者发现所有被漏建模的行为。

## 3. 进展：固定策略的全后继降秩

设目标 `T` 为原验收满足且安全的世界。信息集目标要求非空且全部可能世界满足目标。目标还必须对所有后续允许转移闭合，防止已排队旧请求在“完成”后破坏安全。

对可执行宏动作 `u`，候选获胜区域可以写为：

$$
\mathcal W_0=\{B\ne\varnothing\mid B\subseteq T\},
$$

$$
\mathcal W_{n+1}=\mathcal W_n\cup\{B\ne\varnothing\mid
\exists u:\operatorname{Legal}(B,u)\land\operatorname{PrefixesSafe}(B,u)
\land\operatorname{Terminates}(B,u)
\land\forall o\,[B'_{u,o}\ne\varnothing\Rightarrow B'_{u,o}\in\mathcal W_n]\}.
$$

宏动作必须在每个可能世界中合法，内部允许执行均有限地产生终结观察。不能以“存在一个终结后继”替代“每个实际允许执行都会返回”。环境公平、服务可用、有限故障预算等条件需体现在允许执行合同中；它们不是由队列名称或定时器周期自动获得的。

Lean 本轮**没有实现上述吸引子算法，也没有证明任意程序都能生成证书**。它检验显式证书：固定信息集策略 `policy`、非空信息集、获胜区域闭包、可执行性、宏步有限返回、所有观测后继严格降自然数秩、零秩满足目标、目标后保持。由此证明：

$$
\forall\rho:\quad
[B_0\in R\land\operatorname{Prefix}_{\sigma}(\rho,r(B_0))]
\Rightarrow\exists n\le r(B_0):\rho_n\subseteq T.
$$

`R` 是证书覆盖的区域；`Prefix` 要求在预算范围内尚未达到目标时，每一步都按固定策略完成允许的宏步，达到目标后允许填充。这里的 `n` 是**已经完成的宏步数量**。实际程序必须实现该策略、覆盖所有允许结果，并提供实际执行与观察边界的精化关系。证明另排除认证区域中的非目标死锁，也提供具体的双世界原键恢复证书作为正控。它没有给出秒数上界，也不表示永久不可用的外部服务最终会恢复。

两个 Lean 切片现已使用相同的关系观测：`Progress.lean` 的 `emits : World → Observation → Prop` 允许一个世界产生多个报告，且报告可以错误。`observed_post_iff_evidence_update` 证明进展模块的后继信息集与证据模块的集合更新完全一致。宏步有限返回合同要求每条允许执行在有限 tick 内返回一个 `(World, Observation)` 对，且**所有返回对**均满足转移与报告关系；它不是仅假设“总能选出某个可观察结果”。

0.3.1 的反例 `late_valid_return_cannot_hide_early_invalid` 说明为何需要全称约束：一条执行先返回不满足 `finish` 的结果，后返回合法结果，仍能满足旧的“存在一次合法返回”条件；新合同拒绝该执行。合法返回不表示报告诚实，报告是否可能仍由允许错误的 `emits` 决定。这个改动不证明首个返回时刻或输出稳定性。旧具体轨迹提升另有 `realizesFinish` 前提，因此该反例揭示的是合同过弱，不能反驳原来的条件定理。

这个返回对中的 `World` 是数学执行轨迹的隐藏结果标注，不是提供给 Agent 的额外真实信息。策略仍只依据其信息集，实际报告经同一关系更新信息集。

`MacroRealization` 现在只直接要求**初始**信息集包含真实世界。实现还要提供逐步实际转移 `realizesFinish`、实际报告覆盖 `realizesObservation`，以及按同一关系计算的完整信息集更新。`MacroRealization.possibleAtBoundary` 调用 `update_contains_actual` 进行归纳，推出每个后续边界仍包含真实世界。由此，原来“每个时刻都包含真值”的外部前提已经变为定理；实际转移/报告没有漏建模、策略已采用、边界和中间状态覆盖等精化义务仍未自动满足。

新增的 `deceptiveRealization` 给出持续假报告的具体实例：真实效果始终是 `absent`，每次报告却都是 `claimsApplied`。新接口允许该轨迹，并证明真实世界始终被保留、不能推出验收。`deceptive_only_no_progress_certificate` 进一步证明，这个不变且未达目标的信息集不可能落入任何全后继严格降自然数秩的证书区域。它防止把“模型接纳了轨迹”误读成“模型证明该轨迹会成功”。

有限自然数秩是一个充分条件；不是所有可在公平调度下收敛的异步系统都必须有这种秩。原有 Python 两步示例检查存在成功态和局部死锁，**没有检查所有非终态循环**；一条成功路径不能代替本节的全执行量词。

## 4. 马尔可夫相关问题：先证明压缩保留区别

令 `φ : H → S` 把完整历史压缩为实际保存的状态。对任意 `φ(h₁)=φ(h₂)`，需要逐项检查：

| 需保留的区别 | 精确条件 |
|---|---|
| 当前合法动作 | `Enabled(h₁,a) ↔ Enabled(h₂,a)` |
| 可能的抽象后继 | 对每个动作 `a` 和摘要 `s'`，两历史是否存在到达 `s'` 的后继一致 |
| 原目标验收 | `Acc(h₁) ↔ Acc(h₂)` |

Lean 的 `sufficient_iff_exact_relational_quotient` 证明：**这三条兼容条件，当且仅当这些关系可以准确地仅用摘要状态表达。**这是一个关系语义的压缩准则；不是对真实 LLM 的概率马尔可夫性、平稳性或独立性断言。若需要概率模型，还需证明条件转移概率核在同一摘要内相同。公平性、观察权限及时间界也需额外保留。

两个已证明反例说明了实际设计约束：

1. “尚未发送”与“旧请求在途”可以处于同一节点，但允许新写的条件不同。只保存节点不能准确判断合法动作。
2. 两者都显示“等待”，在途请求却可能随后生效；压掉在途历史会丢失未来转移。

因此，不能从“写出了状态机”推出“当前持久字段已足够”。下一步需要对真实状态序列化、原键、版本、未结责任、在途效果和证据来源构造精化证明或反例。

## 5. 谄媚与共同误判：把报告当任意输入

`Report` 在 Lean 中是任意类型，其内容可以任意变化；没有诚实、独立、无偏或固定错误率假设。报告本身只能更新报告字段。关闭动作必须经过：

$$
\operatorname{Authorized}(w)\land\operatorname{BoundEvidence}(w,e)
\land\operatorname{verify}(e)=\mathrm{true}.
$$

在以下**显式证据可靠性前提**下：

$$
\operatorname{BoundEvidence}(w,e)\land\operatorname{verify}(e)=\mathrm{true}
\Rightarrow\operatorname{Acc}(w),
$$

Lean 对任意有限提交轨迹归纳证明：任意报告更新不能让假任务通过这个门关闭。这里的世界与授权在局部切片内固定；动态撤权、外部晚到效果及所有生产写入口是否经过门，必须另行证明。

同时，Lean 构造了两个反模型：

- **执行者和两个评审者全报 PASS，实际事实仍为假。**一致意见不推出真实验收，也不能默认评审错误独立。
- **保留结构化提交与授权检查，但去掉可靠证据前提，仍存在假关闭轨迹。**字段形状、两个签名或一个 HTTP 200 不能补上语义真值。

另有一个绑定真实 Bool 世界的正控，证明可靠门确实可以接受真成功，避免靠永远拒绝获得安全。这个合成合同不证明真实证据签发者、读取通道或验收器正确。

工程对应要求是：由受控原任务绑定决定读取对象；核对原验收及证据所指的实际事件；保留原始主张但避免把预填裁定提供给中立核验。移除诱导文本只说明输入投影的结构变化，**不证明真实模型消除谄媚或与执行者统计独立**。

## 6. 概率结论仍单独审查

本轮 Lean 使用关系与逻辑，允许非确定的转移及报告，但没有引入概率分布或概率库，也没有形式证明重试概率界。

公开规范采用的条件是：若对每个仍失败的相关历史 `H`，下一次失败都满足统一上界 `Pr(Fₖ | H) ≤ η < 1`，则同一条件下连续 `K` 次失败至多 `ηᴷ`；对 `m` 项责任可用并集上界 `mηᴷ`。这是逐历史的条件界，不要求 IID，但不能以边际错误率或一次成功纠偏替代。责任和条件变化时，也不能把旧预算无解释地重新计数。

仅有每次 `ηₖ < 1` 不足以推出最终成功。例如：

$$
\eta_k=1-\frac{1}{(k+1)^2},\qquad
\prod_{k=1}^{K}\eta_k=\frac{K+2}{2(K+1)}\longrightarrow\frac12.
$$

同样，每一步边际正确率都是 0.99，不会唯一决定 100 步全部正确的概率：独立时是 `0.99^100`，完全共同原因导致全部同时正确或错误时可以是 `0.99`。部署环境的相关性与条件上界需要观测及验证；本仓库没有给它们填入估计值。

## 7. 当前证据等级与剩余义务

| 项目 | 本轮状态 | 下一步需要什么 |
|---|---|---|
| 信息集真值保留 | Lean 条件定理 | 实际观察/转移没有被漏掉的精化证据 |
| 证据与进展的观察接缝 | Lean 更新等价与逐边界归纳；假报告实例及反例 | 初始真值包含、真实返回和完整关系更新的实现证据 |
| 全后继有限秩收敛 | Lean 条件定理与合成证书 | 实际策略采用、宏步终结、所有结果覆盖 |
| 状态充分性准则 | Lean 充要条件与遗漏历史反例 | 对真实持久状态验证这三类兼容性；概率/公平另证 |
| 任意报告与验收门 | Lean 局部不变量与正反控 | 可信证据语义、提交入口完整性、动态世界不变量 |
| 概率重试界 | 文档中明确条件 | 概率形式化及真实参数验证 |
| 完整较新模型迁移 | 未完成 | 后续去敏同步与逐项覆盖清单 |
| 生产无人值守 | 本轮未验证 | 同一原任务、原版本、合法角色和原 AC 的自然全链回执 |

Lean 检查的是这些定义与前提下的推导。把未验证的环境条件当作前提，并不会使它们变成现实事实。后续应优先处理会改变以上前提真假的实现断点，而非增加无关的正常路径 PASS 数量。


## 8. 2026-11-27：消费项目模型试点（0.3.2-pilot）

本轮将 Agent Workflow 中可复用的身份、持久责任、UNKNOWN 与验收边界，落实为两个更窄的转换模型：

- [ExecutionRecovery.lean](lean/AgentWorkflow/ExecutionRecovery.lean)：NodeVisit / attempt / generation 身份不变；planned 与 resolution-blocked 仅在 delivery-start fence 未设置时进入首次投递；UNKNOWN 仅允许只读复查，terminal 仅允许单独的责任交接元数据；两者均不能重新开始投递。
- [Outbox.lean](lean/AgentWorkflow/Outbox.lean)：按 channel gate 约束逐行 claim；event key 不变；UNKNOWN 在重试上限内回到 pending，EXECUTION_KICK 达到第 12 次时 dead-letter；只有 EXECUTION_KICK 可以 dead-letter；已 claim 行不能被第二 worker 再 claim。

这两个模型是可复用的抽象性质，不声称覆盖具体 JS 文件系统持久化、Node.js 多进程锁、PostgreSQL MVCC / `FOR UPDATE SKIP LOCKED`、HTTP 客户端、事务提交或 forum per-instance anti-overtake SQL。消费项目必须提供独立实现映射和运行证据。对应试点：
- [dsh-agent-core #710](https://github.com/mayf3/dsh-agent-core/issues/710)
- [svc-workflow #140](https://github.com/mayf3/svc-workflow/issues/140)

复现：`python3 tools/verify_lean.py --domain agent-workflow`。在该命令本轮实际运行并产生回执前，新增证明状态标记为 PENDING_KERNEL_VERIFICATION。
