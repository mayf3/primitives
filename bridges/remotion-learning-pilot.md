## 1. 当前困难与已存在的能力

目标读者首先是**第一次听说 Remotion 的内容创作者**。其中一部分会 React 和命令行，另一部分只想先判断这个工具适不适合自己。补入口解释不能自动把整门课程改称“零编程基础也能独立完成”。

当前源码呈现的课程首页顺序是：课程标题 → 作品预览 → 首个练习成果 → 先修条件 → 六步首课入口 → 已开放章节。有关 Remotion 定位的内容存在于第 1 章，但默认首课入口并不经过它。首课第 1 步直接解释三个 TODO；第 1 章又从“由帧号决定画面的纯函数”切入。由此提出的设计判断是：普通新手可能缺少理解作品示例及后续操作的概念桥梁。**该困难的发生频率和对真实新手的影响尚未测量。**

下列能力在核对的源码中已经存在，应复用：

| 已有能力 | 证据位置 | 本轮取舍 |
|---|---|---|
| 作品长度与学习投入分开说明 | `course.yaml` 的 `first_outcome`；`FirstProject.tsx` 的首课说明 | 保留区别；本提案不新增耗时承诺 |
| React、TypeScript、命令行先修默认可见；手机预览与电脑导出分开 | `course.yaml` 的 `prerequisites_summary`、`practice_surface`；`CourseHome.tsx` 的条件区 | 保留，并让“先理解”和“实际改造”各有清楚条件 |
| 六步导航可以跳步、返回，显示目标、前提、检查点与卡住恢复 | `FirstProject.tsx`、`steps.tsx` | 复用，不新增闯关或账户进度 |
| 第 3 步已有 30fps、`TITLE_AT` 30→45、18 帧入场的预测与对照 | `TimingCompareLab.tsx`、`steps.tsx` | 作为样板核心，不另造一套视频工程 |
| 参数与预测由首课页保存，切步保留；刷新清空的边界已明示 | `FirstProject.tsx` 的页面状态与页尾说明 | 保留，不在本轮扩跨刷新保存 |
| 网页示意与正式渲染分开；分步模式说明改文字不自动改旁白 | `TimingCompareLab.tsx`、`steps.tsx` 第 3、5 步 | 保留，并修齐全文模式中的对应说明 |

## 2. 学习目标与允许的支持

样板只要求读者能够：

1. 用自己的话说明 Remotion 如何产生视频，举出一个适合自己的用途，并知道实际修改工程需要什么条件。
2. 区分标题“什么时候开始出现”和“入场过程持续多久”。
3. 在 30fps 条件下，预测并验证改变开始帧的结果；再按一个新的开始时刻要求选择参数并说明理由。

本轮不要求证明能手写全部 React，也不把播放、勾选、导出成功等同于理解。

**独立目标与支持工具分别约定。** 例如，“无提示完成帧数换算并解释理由”与“允许 Coding Agent 修改工程、本人判断结果并指导修正”是两个不同的任务条件。后者可以是有效的实际能力目标，但不能被记成前者的无帮助表现。记录是否查看示例、打开哪一级提示、查阅文档、接受人员帮助或使用 Agent；同时记录提示后的结果，不把它们压成一个“通过”。

## 3. 页面与路径层级

### 3.1 课程首页：先交代是什么，再看作品

在标题之后、预览之前默认显示一段短解释。建议中文如下，实施时由课程作者核对并写入内容源：

> **Remotion 是什么？**
>
> Remotion 让你用 React 代码描述视频画面：文字什么时候出现、图形怎样移动，都由代码和时间参数控制，再渲染成视频。它适合结构可复用、需要换数据或精确控制时间的解释视频。这门课先带你看懂“帧数怎样决定画面”，再修改一个现成工程；实际修改和导出需要电脑及下方列出的编程基础。

作品预览继续展示现有 24 秒练习。首页解释“是什么、适合什么”；首课再解释“怎样工作”，避免两个页面复制同一段摘要。

不要求新造三个同等权重的大按钮：

- **第一次听说的人：** 先读默认可见的解释，再进入现有首课。可从已有第 1 章入口进一步了解定位与边界。
- **已有基础的人：** 保留直接进入首课的入口，用已有步骤导航进入“准备工程”或需要的步骤，不强制答一套入学问卷。
- **回来查问题的人：** 使用现有章节、课程路线、视频列表与首课步骤导航。当前源码没有支持的搜索或主题页，不写成已经可用的入口。

既有先修条件继续位于下载、安装之前。“可以先在网页理解机制”和“已经能在本机修改、导出”分别表述。

### 3.2 首课第 1 步：让现有作品成为一个可解释的过程

在看示例处加入最小关系，沿用同一个工程和数字：

> 一帧是一张静止画面。30fps 表示每秒播放 30 帧。代码根据当前帧号计算文字的位置和透明度；连续播放这些画面，就看到运动。
>
> 在这个工程中，`TITLE_AT` 决定开始入场的帧号，接下来的 18 帧决定入场过程。开始时间和入场持续时间是两个不同的量。

把这段解释与示例标题就近对应。需要视觉表达时使用简短的“当前帧 → 画面状态 → 当前画面”关系即可，不增加与理解无关的动效。可以让读者先说一句“我原来以为代码怎样变成视频”，用于发现误解；这不是阻止继续的门禁。

第 1 章开头同步提供日常语言桥梁，再展开函数、组件等技术形式。无需把整章搬到首页。只想在网页体验的人应能明确找到已有第 3 步；本机准备失败时，也能从现有导航继续网页示意，同时知道这并未完成工程安装。

### 3.3 第 3 步：保留现有单变量预测与验证

继续使用现有任务：30fps 下把 `TITLE_AT` 从 30 改为 45，其他量保持原样。先留下预测，再修改、观察并说明差异。示意、代码解释和检查点使用同一组条件：开始晚了 15 帧，入场区间长度仍为 18 帧；开始、接近完成和完成的帧号不能混称。

示范说明为什么选这个量：为了让开始更晚而保留相同运动，移动区间起点，同时保持区间长度。读者需要产出预测或操作结果；要求解释理由时，另外检查其因果说明，不能由选择正确直接推定理由也正确。

### 3.4 一个近变式：改变要求，逐级提供帮助

在同一个网页示意或本机工程中提出：

> 希望标题在第 1.8 秒开始入场，运动方式和入场持续时间保持原样。你会改哪个参数、改成多少？先写下理由，再验证。

**不预填变式答案，也不在任务旁默认展开完整解法。** 观察能否把同一关系用于新要求，暂不另加三段运动、修改 fps 或重建 composition。

提示按需展开：先问开始时刻与持续时间分别由什么控制，再提示秒与帧的换算关系，最后才给完整解释。打开提示本身属于支持条件，不据此羞辱、扣分或中断学习。

维护者核对答案：30fps 下 1.8 秒对应开始帧 54，入场完成帧为 72。这个答案用于反馈与验收，不放进初始输入值。该任务至多提供同一关系下的近变式证据，不能推出掌握整个 Remotion、远迁移或长期保持。

### 3.5 结束与续接

完成网页任务后，可选择继续现有工程修改与导出，或到现有时间模型章节检查问题；明确各后继增加什么。暂未具备本机条件的人可以在理解任务处结束，不显示已导出。

延后检索可以留作后续真人观察：再次给一个等结构、不同数字的短任务，记录实际间隔与帮助条件。本轮不为此建立提醒、打卡、账户或新进度系统，也不承诺某个固定间隔就是最佳安排。

| `platform/src/firstProject/TimingCompareLab.tsx` | 为变式提供与题目绑定的输入和反馈；对齐支持范围与可观察范围 | 复用现有插值示意，不另造计算模型 |
| `platform/src/pages/FirstProject.tsx` | 修清单确认语义、分步/全文资源可达性；必要时承接变式状态 | 不声称网页能检测本机导出 |

`platform/scripts/sync-content.mjs` 当前已经将完整 `course.yaml` 转为 `course.json`，并复制课程 Markdown。新增课程字段不需要另写一套转换；使用既有同步流程重新生成即可。**不要只改 `public/content/`、构建产物或线上副本。** 既有 `vid-04-first-project` 仍是作品与时间参数的来源，本轮不需要换掉 24 秒工程。

### 4.2 清单确认：当前源码仍脱节

在本次基线的 `FirstProject.tsx` 中，`checks` 与 `confirmed` 为独立状态；确认按钮只切换 `confirmed`，没有检查清单内容，取消某一项也不会撤销整体确认。这是源码可复核的关系，不是本页新增的点击结果。

最小修法：让“我已检查以上各项”与所有自查项一致，未全勾时说明剩余项；取消任何一项后撤销整体确认。也可取消冗余整体按钮，只显示逐项自查状态。无论选哪种，“我的自查”都不能升级成平台已验证导出或掌握。

### 4.3 全文与分步：资源和完成含义须一致

基线的全文分支只渲染 Markdown；文档却写“本页上方播放器”“本页顶部按钮”。分步模式才注入播放器和下载控件。全文还使用另一套清单与“全勾即完成首课”表述，并遗漏分步模式已有的“改文字不会自动改旁白”说明。

最低成本修法是在 Markdown 中提供现有示例视频路由和真实 ZIP 下载链接，删除无对应控件的相对位置措辞；同步旁白边界与自查含义。无需在全文中复制整套互动组件。入口可达、任务等价、能力边界一致后，再决定是否保留“全文与分步内容一致”的绝对表述。

页面与 Markdown 的“每步先预测再验证”也应改成“关键改动先预测，再验证”，不为下载、导出强加没有学习目的的预测题。

### 4.4 反馈和可观察范围：变式不能沿用固定答案

基线 `TimingCompareLab.tsx` 的结果主体按当前参数动态计算，但预测回显写死“晚 0.5 秒、运动不变”。此外，输入接受 0–300，滑块与轴只覆盖 0–90；较大的合法输入无法在当前观察范围看到入场完成。

变式实施时须修两种对应关系：

1. **题目与反馈对应。** 原 30→45 题的预测回显明确属于原题；变式的反馈按变式输入和目标计算。修改参数后，不能拿原题的固定 0.5 秒当作当前结果。参数恢复也不能静默清掉原预测或混写两道任务。
2. **输入与显示对应。** 本样板可以把网页示意支持范围明确收窄到 0–72 帧，让当前 0–90 帧轴覆盖整个 18 帧入场过程；同步输入约束、提示与错误文案，并说明这是本练习示意范围，不是 Remotion 的能力限制。若实施者保留 0–300 输入，就必须让轴、滑块、刻度及标记共同覆盖当前开始帧加 18，不得仅改一处最大值。选择以能完成本样板且保持可读为准，回执写清采用哪一种。

不要因为一个输入被组件接受，就把它当成实际 24 秒工程中一定可见、可播放的条件。网页示意与本机真实结果继续分别验收。

## 5. 原语怎样参与本样板

下表只说明可组合的动作和本次任务输出，不主张九项是数学上不可约的最小集合，也不要求每个页面完整跑完九项。

| 学习候选 ID | 在本样板中的作用 | 所需输出或后续证据 |
|---|---|---|
| `learning.elicit-starting-model` | 用一句话或简短预测暴露原有理解 | 初始解释、判断或预测；不是问卷完成率 |
| `learning.relation-model` | 提供帧号、开始时刻和画面状态的关系 | 关系说明已呈现；能否预测改变的影响及不变项另由任务观察 |
| `learning.worked-process` | 在现有示例中解释为何移动入场区间 | 关键决定与结果之间的对应 |
| `learning.elicit-performance` | 要求预测、改参数并观察 | 学习者实际产出，不由看过页面推定 |
| `learning.explain-reasoning` | 专门要求说明为什么改该参数 | 可检查的理由；其是否应独立保留仍受领域评审约束 |
| `learning.feedback-retry` | 指出当前值、目标差异和下一次可改之处 | 错误后重试的过程与结果 |
| `learning.fade-support` | 在变式中先不给完整解法，按需提供提示 | 不同支持条件下的表现，分别记录 |
| `learning.vary-conditions` | 将开始时刻改为新的要求 | 同一关系下的近变式表现 |
| `learning.delayed-check` | 后续观察保持，不作为本轮软件功能 | 实际间隔、提示条件与延后表现；未做则保持未验证 |

设计领域负责读者能看懂页面用途、知道去向与条件、对应参数和结果、保留重试与返回；学习领域负责任务究竟要求何种表现以及什么证据支持该判断。清楚的界面不能自动证明学习，内容有解释也不能自动证明读者找得到入口。

## 6. 有限验收与收口

### 工程与内容检查

只覆盖这条样板及受影响回归：

- 新字段通过既有校验与构建；没有入口解释的其他课程正常显示。首页、分步、全文和第 1 章对核心关系、先修、资源位置与能力边界口径一致。
- 从课程页进入首课，使用现有步骤导航；检查章节、视频、下载、返回与前进后退。没有把未实现入口写成可用功能。
- 原任务 30→45 时开始晚 15 帧、入场长度仍为 18 帧；变式正确输入时开始帧 54、完成帧 72。当前输入、画面、轴、检查点与反馈一致。
- 合法范围边界、非法输入及恢复行为与文案一致；变式初始没有填好答案。切步、切阅读视图不错误覆盖原预测；刷新策略仍如实显示。
- 清单未全勾不能显示“以上各项已检查”；确认后取消一项，整体状态随之变化。全文也不把自查写成系统掌握认证。
- 检查桌面和选定窄视口（可沿用 320/390 CSS 像素），观察标签、单位、提示和对应关系；检查键盘焦点与操作。需要缩放检查时与窄视口分别记录；模拟不等于真机。
- 若本轮实际下载、安装、修改、导出未执行，回执明确未覆盖，不据网页按钮或源码推定端到端完成。

完成相关检查后收口，不因已经做了样板就扩成全站重写或全面视觉迁移。

### 真实学习者观察

先观察目标明确的小样本，分别记录背景与任务条件，不用预设百分比掩盖个体错误：

1. 入口之后能否用自己的话说出 Remotion 的用途、适用任务和实际操作条件。
2. 能否区分开始更晚与运动更慢；错误是概念不明、换算错误、控件误解还是看错反馈。
3. 变式最初怎么做、用了哪种帮助、怎样修正；无提示表现与提示后表现分别记录。
4. 允许 Agent 时，人能否说明要求、发现不符合要求的结果并提出有效修正；不把 Agent 完成代码等同本人独立推理。
5. 如做延后检查，记录实际间隔、题目变化和帮助条件；未做时不声称保持或迁移已验证。

工程可达性与任务定义可以由实施者检查；“目标读者自然找得到、理解了、能够迁移”需要对应观察。继续分开记录来源、实施与用户验证，不新增一个笼统的“全部通过”。本页当前只是一份方案，网站实施为 `planned`，真实学习者验证为 `untested`。
