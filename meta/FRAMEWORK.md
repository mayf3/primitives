# 完整框架：怎样构造领域原语

**目标是用较少、可解释的基础区别与局部规则，组合出有用的方法；每一次简化都应说明保住了什么能力、删去了什么负担。**

本稿版本 **0.1.0**。它是本次对四域方法的综合提案，不是现有来源中已经存在的一套公理，也不追认各域当前数量为最小集合。[来源与推导边界](SOURCES.md)逐项说明依据。

<a id="definition"></a>
## 一、原语究竟是什么

**领域原语，是在明确任务范围、表示方式与成本约束下，为区分和构造有效结果而保留的基础定义或局部规则。** 它是否足够基础，要看删除、替换或继续拆分后，是否还能保住必要区别，并以可接受的代价完成任务。

“基础”有工作尺度。像素比镜头更接近渲染，字词比段落更接近文本存储，却未必更能帮助人解释一段关系或组织一个论点。对于语法分析器，句法可以是研究对象；对于固定材料的文章改写，材料与主张的关系可能才是当前需要处理的对象。**追到底层，要追到能解释当前失败、指导下一步改变的层级。**

原语也不必全是动词。人生领域需要分清观测与判断，还需要说明什么关系构成对判断的证据；写作与交互则主要提供可调用动作。这些角色都可以被精确定义，但不因此成为同一种东西。

“原语系统”可以保留便捷组合、派生视图和示例。**可复用不等于不可再分，容易调用不等于逻辑基础。** 一个名字在目录里占一行，不是它属于基底的证明。

### 从数学公理的类比中保留什么

| 需要交代的内容 | 在方法系统中怎样做 |
|---|---|
| 基础词汇 | 说明什么算同一个对象，哪些情形必须区分 |
| 基本约定与约束 | 声明任务、允许的改变、不能被破坏的关系 |
| 构造与推演规则 | 说清从哪些输入，在什么条件下，可以得到什么产出 |
| 推导 | 展示一个复杂方法分别调用了哪些规则，哪里加入了新判断 |
| 检验边界 | 区分定义自洽、实施符合定义和人实际受益 |

这些角色不能混用。例如，“采用统一单位进行数值比较”可以成为本次任务的约束；“两栏布局更容易理解”则是待检验的实现判断。不能把后者命名成公理，就当作已获得证明。

本系统借用的是**定义清楚、前提显式、推导可追踪**的纪律。自然语言规则还没有被完整形式化；也没有穷尽任务全集。不能从这些定义演绎出某篇文章必然好读、某个界面必然好用，或当前集合全局最小。

## 二、分清角色，才能判断该不该合并

以下是审查问题的不同位置，不是各域必须采用的统一类型表。

| 角色 | 直接回答什么 | 例子与边界 |
|---|---|---|
| 对象定义 | 什么必须被稳定识别？什么算一项，何时仍是同一项？ | 人生的 Observation 与 Claim；页面不因此变成人生 State |
| 关系定义 | 哪些对象在什么条件下相连？ | 一条观察在指定范围支持或反驳判断；“有关”还不足以说明关系 |
| 动作规则 | 给定输入，直接作哪项决定或改变？ | 选择适合当前目标的后继，或修复一句话的支持关系 |
| 约束与原则 | 哪些条件必须保留，怎样取舍？ | 固定材料改写不暗增事实；它本身未必是一项操作 |
| 组合与派生视图 | 怎样组织已有能力，减少重复推理？ | 学习路线、任务终点接续；Life State 的当前快照有派生来源 |
| 表现与实现 | 用什么形式把规则落实？ | 连接词、两栏布局、折叠控件、剪辑、动画、软件 API |

一个实现可以服务多个动作，同一动作可以有多种实现。按钮可以进入课程、提交输入或撤销修改；“加按钮”没有说明需要哪一种任务关系。箭头可以表达先后、依赖或因果；画出箭头没有决定哪一种关系为真。

表现并不天然次要。诗的节奏、作者声音、视频感受都可以是任务本身。此时它们需要自己的判断标准。要避免的是**用一种惯用形式替代对当前任务的判断**，而不是把审美或语法从系统里剥掉。

角色之间允许依赖：证据关系需要连接对象，动作需要输入，模式需要动作。**职责能分清，与实际工作密切配合，可以同时成立。** 独立不是互不接触，更不要求每项都能单独完成整个任务。

## 三、先约定领域边界

设计新集合或争论最小性之前，先留下四项简短约定：

| 约定 | 要回答的问题 |
|---|---|
| 任务与排除项 | 谁在什么场景做什么？本轮不试图解决什么？ |
| 有效结果与失败 | 怎样判断任务满足？哪些具体错误不能接受？ |
| 表示与默认能力 | 已经允许哪些语言、工具、材料和外部判断？什么被当作已知输入？ |
| 成本边界 | 学习、选择、准备输入、组合、执行、维护和修复中，哪些负担需要降低？ |

例如，固定材料的写作修订，可以要求保留事实、允许编辑新解释、让读者看清论点与依据；自由小说允许新增虚构事件。两种任务不能用同一条“不得新增内容”规则处理。

默认能力尤其容易被遗漏。如果删掉“选择比较维度”，但输入改成“编辑已经正确选好了比较维度”，工作仍然存在。它可以合法交给上游，但必须说明是谁负责、代价怎样计算；不能由此宣称整个系统少了一项判断。

没有必要先为整个世界建模。用一个具体困难或目标样例和相邻反例开始；当前任务能启动、关键区别已经明确时，可以停止继续追问更底层的词。新的失败再打开边界。这与人生来源将 Goal 设为操作性约定终点的做法相容，参见[来源说明](SOURCES.md#repository)。

## 四、构造问题一：必须保留什么区别

**从一个具体任务开始：它可以是已经发生的失败，也可以是尚待实现的目标。找出哪些混淆会影响有效结果，说明这是实际观察，还是构造的对照。**

### 怎样做

1. 写出输入、预期产出，以及已经观察到的失败或需要排除的混淆。不先用“缺少高级感”“不够流畅”“信息太多”概括原因。
2. 提出两个表面相近、却应当得到不同处理的情形。指出差异落在对象身份、范围、关系、条件、承诺还是感受目标。
3. 换一种合理表现形式，观察这种差异是否仍需要被保留。由此提炼可复用结构，而非只提炼共同词语。

例如，“某人说过 X”和“X 得到证据支持”都可能写成一句话，但需要不同处理；“按钮准确描述目的地”和“目的地适合当前目标”都帮助导航，却不是同一个判断。

**产出：** 一小段必要区别及其理由，附一个需要区分的对照。它不是新的全域对象本体，也不要求给每句话编号。

### 保留什么，允许改变什么

对每次变换，说明哪些关系不能丢失，哪些内容可以创作。固定材料可以重述，解释可以新提出，但材料来源不能被反写；自由创作允许改变情节，仍可能要求人物设定和叙事目标保持连贯。

“不变量”只指**当前任务要求保持的东西**，不意味着所有任务都冻结内容。新发现也可能推翻此前约定；此时应更新约定，而不是把冲突藏在实现中。

### 什么不算完成

把“这段不好懂”改叫“认知负荷高”，仍未说明哪里出了问题。把所有情况命名成“关系”，却不区分因果、对应、先后、包含与来源，也没有获得可用结构。

换表现形式后困难得到解决，只能说明这一情境可能已不必继续干预，不能据此把整个候选降级。要继续追问：新的实现是否仍保留了同一必要区别？若是，换掉的是实现，语义责任仍在。只有候选实际只是某个实现的参数差异、没有额外判断时，才有归入实现层的理由。换媒介也不能要求所有领域动作适用于所有媒介。

## 五、构造问题二：直接负责什么，怎样接上其他部分

**把识别标准、局部责任与组合条件说到可操作。** 好的名字应让人知道何时调用；完整定义则应让人知道调用后能得到什么、不能据此宣称什么。

### 依角色写清定义

| 当前设计的是 | 至少说明 |
|---|---|
| 对象 | 识别条件、身份与范围、与邻近对象的区别、信息从哪里来 |
| 关系 | 连接谁、方向与类型、成立条件、不成立或未知时怎么办 |
| 动作 | 触发与输入、直接决定或改变、产出、必须保持的约束、失败或缺输入时怎么办 |
| 组合／派生 | 调用哪些已有定义、输入输出怎样连接、仍新增了什么判断、为什么值得保留入口 |

这些是定义责任，不要求各域使用相同字段、状态机或证据枚举。[轻量卡](TEMPLATE.md)只是编写辅助。

对动作可以用一句话写成：**在条件 P 下，使用输入 I，由本项负责变化 Δ，产出 O，并保留约束 K。** 这是检查说明是否齐全的句型，不是声称现实行为已经成为确定函数。

例如，“预告入口结果”的输入是已存在的入口与真实目的地，改变的是点击前线索，产出是可核对的入口表达。它并不承担挑选合适后继的全部判断。若把后者也悄悄写进“优化链接文案”，就扩大了责任，而不是完成合并。

### 一个复杂方法何时算被推导出来

至少要看得见以下交接：

- 后项要的材料、范围、单位、来源与判断状态，是否由前项产出或明确外部输入提供。
- 前项没有提供的决定，由哪个步骤负责。未知项能否保留，而非默认成已成立。
- 后项是否保留前项仍然有效的约束；若有合法改变，谁授权、在哪里说明。
- 输入不足、条件不成立或执行失败时，是补材料、退回、改路线，还是停止。

把“理解 → 表达 → 行动”连成箭头还不是推导。“读过概念页”也不能直接接到一个要求“已经掌握概念”的任务门槛，中间需要相应能力依据，或把门槛改成实际已知的条件。

把新增判断写明，能使方法说明完整；只有这些判断也由既有规则或预先声明的外部输入承担，才能进一步称该方法已由当前基底构造出来。显式增加一条新规则可以有价值，但不能把它同时计为旧基底已经具备的能力。

组合可以有分支、复查和返回，不必是直线。返回原题修正输入可以推进任务。只有互相指称、没有独立判定办法的定义循环需要修复；有可识别状态、推进依据与停止条件的工作循环并不因此有错。

### 基底与快捷入口可以并存

若一项可以由现有规则完整构造，且没有藏着额外判断，可以把它解释为组合。频繁使用时，仍可保留简短入口来降低调用成本。SICP 区分基本表达、组合与抽象；这里借鉴的是分层和命名组合的方法，不是从程序语言中直接证明人类创作规则。[一手依据](SOURCES.md#sicp)

划分责任时，也应考虑哪些决定需要独立理解和改变。Parnas 对模块分解的研究为这个问题提供参照；本稿将它用于方法拆分，是新的类比，不是原论文对这些领域的结论。[一手依据](SOURCES.md#parnas)

## 六、“最简”怎样成为一个可检查的主张

本稿把最简化的工作目标写成：**在保住约定任务质量的前提下，降低整套方法的总使用负担。**

要一起看定义和分支的复杂度、学习与选择成本、准备输入的成本、组合和执行成本，以及误用后的修复成本。当前没有统一权重，也没有量化最优解。具体取舍必须回到领域约定；不能拿一个未经验证的总分抵消必要的质量底线。

### 两种假极简

**只留一个“优化”。** 数量最少，但所有判断被藏进参数、解释、使用者常识或模型能力。“如何优化”仍要重新发明。这是少写了模型，不是消除了工作。

**拆到只有“增字、删字、换字”。** 可以生成大量文本，却没有告诉作者材料怎样支持结论、为何选择这个切口。形式操作变少，决定怎样使用它们的成本可能更大。

因此要分别计数基础区别、动作、组合入口与实现选项。Life 的 State 可以有派生来源而保留为一等使用对象；写作的“定向修补”可以调用其他动作。它们有使用价值，并不自动意味着它们是逻辑不可约的基底。[四域实例](EXAMPLES.md)

### 三种强度不同的“独立”

| 能说的结论 | 需要什么依据 | 不能顺势推出什么 |
|---|---|---|
| 两项职责可区分 | 存在需要 A 而 B 不能单独替代的具体情形，反向也可检查 | A 不能由 B 与其他项组合 |
| 相对当前集合暂不可删除 | 固定任务、默认能力和成本，移除 A 后用所有剩余项重建，仍有能力缺口或成本超限 | A 在所有任务和表示方式中都必要 |
| 形式逻辑独立或全局最小 | 明确形式语言、推导规则与比较范围，并给出相应证明 | 不能用几个自然语言例子替代这些证明 |

即便当前集合中的每一项都经不起单独删除，也只说明在这个集合和测试范围内没有找到冗余；另一种表示可能用更少的项完成工作。局部不可删，不等于全球最少。

“完备”同样需要范围：覆盖已收集案例、覆盖当前约定任务、覆盖领域所有可能任务，是不同主张。前两项也要有明确任务记录；本文没有证明第三项。

## 七、构造问题三：用什么反例修订它

检验应从当前争议出发。新增候选至少应说明正例、边界和一个可能淘汰它的测试；无需为每次普通调用执行下面所有检查。

| 争议 | 检查怎样做 | 什么结果值得改变定义 |
|---|---|---|
| 是否只是形式技巧 | 保持任务，改措辞、版式或实现；必要时换一个合理载体 | 换实现仍需承担同一决定，就保留语义责任；差异仅为已有规则可吸收的实现参数时，才考虑归入实现层 |
| 两项是否重复 | 用邻近情形分别调用，再用另一项或组合替换；记录未被承担的决定 | 输入、责任和产出相同，仅参数不同，可合并；不能靠共同目标直接吞并 |
| 一项是否过大 | 尝试拆成不同决定，观察它们是否分别出现、分别选择或分别失败 | 有独立触发和产出的部分可分开；两个动词不自动等于两个原语 |
| 一项是否可删 | 移走它，用剩余集合重建相同任务，并记下额外说明和上游准备 | 无能力损失且总成本可接受，可删除或降为组合；隐藏补回不算成功 |
| 组合是否成立 | 检查每个交接所需的材料、语义、条件和状态，注入一次缺输入或失败 | 接不上时补接口或承认缺项，不用“大模型会处理”填空 |
| 是否只是为例子量身定做 | 定义冻结后，用未参与定义的任务，由另一位使用者独立选项和组合 | 新的遗漏或误用用于修订；改过定义后该例不再算下一轮未见案例 |

“未见案例”检查方法能否迁移；真人试用检查人能否有效使用。Agent 可以帮助构造反例、找漏项和做一致性审阅，不能冒充真实作者、读者或观众的效果数据。

### 检查后必须作一个明确处置

可以保留，收窄或改写，拆开，合并，降为组合／派生视图／实现，移出当前范围，或暂留未决。保留时说明尚未解决的反例；降为组合时保留必要的使用入口；无法判断时记录缺少什么观察。

不要因一个案例成功就新增原语，也不要因某次任务不需要它就全局删除。新增项应提供现有集合未承担的区别或决定，以及预期重复出现的任务范围；是否稳定复用，继续靠后续实例检查。

### 分开记录三类结果

| 结果 | 可以据什么报告 |
|---|---|
| 定义与推导检查 | 对照原定义、输入输出、反例和引用，指出实际检查范围 |
| 实施检查 | 具体代码、稿件、页面或视频是否真的完成所述改变 |
| 使用效果 | 相应作者、读者、操作者或观众在什么任务中的实际表现 |

三类不是统一的状态机，也不互相自动推出。来源已核对不能推出内容全部正确；结构校验通过不能推出方法必要；按钮出现、视频渲染、作者选稿也不能推出学习或理解发生。

## 八、把这套方法用于它自己

本层的任务是帮助维护者设计和修订领域方法，默认读者能阅读自然语言定义和合成例子，成本目标是减少含混责任与无效扩张。日常调用者无需先读完整理论。

本版保留三个构造问题，因为：没有必要区别，候选会停在抽象口号；没有责任与组合条件，候选无法使用；没有淘汰方式，数量只会增长。这些是当前保留理由，**不是对三个问题已充分且最少的证明**。

边界约定可以和候选同时迭代；三个问题也可以在一次修订里一起处理。没有必要要求严格按固定顺序填写，也不建立更高层审批。若新领域显示需要新的责任，或另一种写法以更低成本覆盖同样问题，就修改本层。

本次案例取自已有四域及明确标为合成的新例，主要检验解释是否一致。它们已经参与构造，因此不能再作为本版的未见案例。下一轮应选其他任务，保留定义冻结点与具体结果；没有新失败或新取舍依据时，可以停止本轮修改。

进入实际维护时，按[构造卡](TEMPLATE.md)记录必要信息；改变含义再记录版本与兼容影响。原始材料保持原样，新解释另有归属。各域按自己的规则演进，实际跨域交接继续留在 [bridges](../bridges/)。
