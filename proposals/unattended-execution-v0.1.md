# 无人值守执行原语候选 v0.1

**状态：候选方法稿，非已证明最小原语集，非 accepted Spec，非生产授权，非运行实现。**

编写日期：2026-11-13。本文把此前会话提出的五项区别——任务义务、有类型的证据、受控动作、执行尝试、持久后继——记录为可审查候选。归档不表示系统已经无人值守。

本稿尚未注册为 `registry.json` 的正式领域模块，现有 CLI 的领域索引不会自动加载它。先验证一个具体用途，再决定是否按仓库共享约定建立独立领域及索引；不改变人生、写作、设计、视频四域的定义，也不把同名概念自动视为同一个对象。

## 1. 任务边界与默认能力

### 目标

人类提交的任务持续由系统负责。条件具备时，系统无需人类协调即可执行；遇到技术失败时，自动运行正式治理/Debug/修复/发布/恢复工作流，最后回到原业务并按原标准完成。

**不由 Agent 评判任务是否过时或值得继续。** 等待时间只用于发现停滞、安排重试和升级，不是取消任务的依据。只有人类明确取消才退出业务义务。可以停止一次不安全的尝试，但不能因此伪报完成、取消原任务或无限重试。

### 假设与限制

默认复用既有身份与授权权威、业务 Workflow、持久记录、正式操作入口、受控执行器、版本化制品、独立验收和可恢复的底层进程托管。哪些能力缺失，应明确报告并由原工程责任补齐；不能藏在“可靠底座”四个字里。

这里不保证任意现实任务都能完成：外部服务可能永久不可用，必要权限可能未被授予，模型可能不会解题。此时保留原义务和具体阻塞，不越权、不伪造、不擅自取消。真实人类输入与技术协调分别记账。

仓库只保存方法、脱敏合成反例和验证设计。真实任务、完整UUID、会话、生产日志、凭据和审批原件留在原业务系统。本文不安装工具、不新建 Scheduler、数据库、权限中心或第二套权威账本。

### 要减少的成本

不是减少所有思考，而是减少每次执行都必须由模型重新作出的控制判断：抄坐标、判断回执属于谁、选择下一执行者、发现旧结论已撤回、识别是否需要重试等。模型用于局部求解；控制流程不能靠它记得“下一步”。

## 2. 五项候选：先保留区别，不先发明五种表

这些局部名称只用于本文，不是已经分配的领域ID或要求新增的生产字段。

| 候选 | 类型/直接责任 | 不可混淆的邻近项 |
|---|---|---|
| 任务义务 | 对象；稳定识别用户要求与原完成标准 | 一次尝试、一个会话、一条消息 |
| 有类型的证据 | 对象及支持关系；限定事实能支持的结论 | 假设、解释、无范围的PASS字符串 |
| 受控动作 | 动作合同；限定前置、权限、效果、验收 | 任意自然语言委托、全权工具调用 |
| 执行尝试 | 对象；某动作的一次受控运行及其结果 | 业务操作身份、业务义务、进程代际 |
| 持久后继 | 关系及可消费责任；保证结果之后仍有人/程序负责 | “下次再看”的文本备注、一次通知ACK |

### 2.1 任务义务

**识别标准：** 来自同一委托的目标、验收范围和明确变更记录。某次worker替换、会话重建、代码更新或合法后继承接，不创建新的业务意图。

**所需输入：** 可信委托、原完成标准、已有授权范围、当前任务的权威身份。任务内容改变须有相应依据，不能由实现方便决定。

**允许变化：** 执行方式、角色的合法继任、诊断与修复路径；这些变化保留原目标和已发生的效果。用户明确修改或取消时，按正式入口记录。

**退出依据：** 原目标已由足够证据证明完成，或用户明确取消并得到合法处理。失败、超时、预算用尽、换会话、创建后继均不是完成证明。

**最小正例：** 写作任务的一次worker失败，原任务仍在；受控修复后另一个合法执行者继续未完成部分。

**相邻反例：** 某次attempt结束，系统顺便把整个用户任务记为done；或任务很旧就自动退役。

**删并检验：** 若只保留attempt，如何表示多次尝试共同履行同一任务、以及只取消单次尝试？若补入父任务标识和完成标准，说明这项区别仍未消失。未据此证明必须有独立实体表。

### 2.2 有类型的证据

**识别标准：** 来源、对象身份、版本/代际、观察范围、取得时间、方法和结论边界。需要保护的证据只保存原权威引用；模型文本本身可以是“模型报告过X”的证据，不自动成为“X为真”的证据。

**支持规则：** 证据只有在对象、版本、范围和来源均符合目标判据时，才支持该结论。查询失败、查无权限和真实不存在必须区分；UNKNOWN不能静默变成否定或肯定。

**输入不足：** 产生一项有边界的补证动作，或保留明确未知状态。不能根据“没找到同名工具”断言整个产品没有能力。

**最小正例：** 可信授权入口确认指定主体/客户端/资源的执行能力；这可用于判断是否需要追加相应Grant，仍不代替业务角色/Case/写入门检查。

**相邻反例：** 一次只读请求的token没有执行scope，便断言该主体不具备获取执行token的许可；另一个主体读取404也不能支持这个断言。

**删并检验：** 将证据降为普通字符串后，是否还必须额外保存对象/版本/权限来源和支持关系才能避免上述误判？如果必须，说明这项语义没有被删除，只是藏进了别处。

**边界：** “假设”不是第六个基础原语的既定结论。当前把假设视为尚未满足判据的候选命题：可以触发检验，不能直接修改权威业务状态。后续实践可决定是否需要进一步拆分。

### 2.3 受控动作

**识别标准：** 一个明确操作合同：输入、前置条件、执行资格、允许效果、成功判据、失败类别和结果未知时的处理。

**所需输入：** 任务义务、准确对象和版本、必要证据、可信授权、可用工具及环境。默认能力都必须由上游实际提供，不能让模型猜UUID、环境、权限或测试入口。

**允许变化：** 只改变已批准范围内的对象。生成候选代码不等于获准部署；允许加购不等于允许付款；只读核证不应通过生产写入试探权限。

**最小正例：** 在准备好的隔离工作区中修改一个函数，交出候选工件；固定验收器与独立QA验证后，另外的正式发布动作才可能生效。

**相邻反例：** “读懂所有Issue，找出所有问题，自己申请权限并把全系统修好”作为一个动作，既无封闭输入也无清楚验收边界。

**删并检验：** 只有任务目标而没有动作合同，是否仍需执行者临场决定权限、效果和验收？这些额外判断必须计入成本，不能靠把它们放进Prompt宣称已简化。

### 2.4 执行尝试

**识别标准：** 对确定动作的一次运行；关联原任务、业务操作、节点访问、attempt和适用的进程代际。它们是不同身份，不能混为一个generation。

**责任：** 记录开始、执行占用、完成/失败/结果未知及真实产物；在原子状态提交点检查身份和版本，旧回执不能结清新尝试。恢复遵循既有授权与CAS合同。

**副作用规则：** 同一业务操作跨attempt保留效果身份。可重试的查询与不可盲重做的外部效果分开；效果UNKNOWN时优先读回，不通过换requestId重新做一遍。

**最小正例：** 外部效果可能已发生但回执丢失，恢复者按同一operation读回；确认已有结果后记账，不重复效果。

**相邻反例：** 新Agent会话启动，就把原操作当从未发生；或让旧候选的QA结果放行新候选。

**删并检验：** 只用一个“任务状态”能否同时表示旧尝试的迟到结果与当前新尝试？如果必须引入尝试身份，该区别仍然必要。

### 2.5 持久后继

**识别标准：** 对未完成义务的下一项实际处理责任，具有准确对象、可信权限、可运行消费者、触发条件/下次检查和失败后去向。可等待真实外部依赖，但必须明确谁观察恢复以及怎样继续。

**建立规则：** 处理本次结果时，同时决定并可靠保存下一责任。单服务内尽量同事务；跨服务复用现有Outbox、幂等和读回，不假装跨服务ACID。

**完成规则：** 下一消费者实际接收和执行后，仍按其结果继续处理；一次发消息或收到ACK不能结束原义务。

**最小正例：** worker返回无工件FAIL，程序根据既有规则持久化修复责任；重启后仍可重新发现，不等用户再发“继续”。

**相邻反例：** 文档写“原作者下窗接续”，但没有真实执行对象或消费者。结构化FAIL写入History后，没人继续处理原任务。

**删并检验：** 保存任务、动作与attempt却删除后继规则，能否防止“失败已记录但永久无人执行”？若只能靠人记得继续，就尚未重建同等能力。后继可以派生或与现有记录合并，并不要求另一张状态表。

## 3. 从候选推导三个控制不变量

以下是需要实现和检验的设计约束，不是已有生产证明。

### 责任连续

对于已接受、未完成、未被用户明确取消的任务，至少有一条可核路径：合法运行中的attempt；可被消费的持久动作；有恢复观察者的真实依赖；或已可靠送达的必要人类输入等待。没有这些路径时，判为覆盖缺口，不能以任务文件仍存在代替活性。

### 证据相容

状态改变只接受符合对象、版本、权限范围和判据的证据。观察→假设→已证结论不能无条件连跳；Agent解释不能替代权威来源。修复代码通过测试也不能反向证明原生产效果发生。

### 效果与后继不丢

结果可信且满足动作合同，才能提交相应状态；原义务未完成则持久保留后继。重复事件、崩溃、晚回执不能重做效果或丢掉后继。这里追求实际业务效果的受控幂等，不声称在任意外部系统实现全局exactly-once。

**条件性活性：** 当依赖最终恢复、权限合法、资源可用、调度公平且执行者有能力时，合法工作应继续。若模型不会求解，可靠调度不能把不会变成会；必须另测模型能力、改任务/工具或采用更合适的求解方法。

## 4. 治理和Debug如何由这些原语组合

治理不是另外一种万能智能，也不是第六项已经证明的原语。它是上述对象和规则的组合：

`原业务受阻 → 同一阻塞的治理义务及持久后继 → 诊断动作 → 修复候选 → 验收证据 → 必要的更新/发布动作 → 生效读回 → 原Case复核 → 原业务恢复 → 原目标完成`。

每个箭头都必须对应真实入口和消费者。共用故障家族可以共享修复，但原业务分别保留义务与效果关联。

治理worker失败也由同一套attempt与后继机制处理；不能无限递归创建“治理的治理”。固定技术失败走受控恢复，未知问题进入有预算、有输入、有验收的求解活动。不可变STOPPED事实不直接改回PENDING；需要时按原合同建立合法后继。

流程引擎或调度器本体停止时，依赖既有进程托管和受控恢复入口。不能要求已停止的同一个调度器自己启动修复自己的任务。这是明确底层依赖，不是再搭第二个业务调度器。

**治理结束不等于原任务完成。** 治理结果先触发原任务复核；原消费者继续工作并满足原验收标准，才算该业务完成。修好一个Case不等于其他阻塞消失。

## 5. 程序与模型的职责边界

| 决定 | 默认承担者 | 模型允许做什么 |
|---|---|---|
| 当前对象、完整ID、候选摘要、回执关联 | 权威读面与可信任务包构造 | 报告异常，不能猜值补洞 |
| 权限判定、写入准入、重复效果保护 | 既有可信服务端 | 提出核证请求，不自授权限 |
| 后继生成、超时、重启恢复、已知失败分流 | 既有Workflow/调度/恢复代码 | 不承担记住下一步的义务 |
| 跨层未知原因 | 限定范围的诊断活动 | 提出假设与可检验预测，不直接宣称已证根因 |
| 代码/内容候选 | 有能力且被授予局部工具的worker | 产生工件，不自行放行 |
| 工件语义质量 | 独立验收及必要语义审查 | 可参与审查，但其准确性要单独校准 |

“改为程序控制”不等于硬编码所有业务。固定的是身份、证据、权限、结果和后继的语义边界；业务图和获准策略仍可配置。

## 6. 三个合成反例：用于检验，不是新的生产取证

以下反例由此前会话中的失败模式抽象而来，不复制私密运行数据，不宣称测试已运行。

### 例A：只读token与执行Grant

同一主体可拥有read和execute两种许可，某详情工具本次只申请read token。它返回MISSING_EXECUTE_SCOPE，只支持“本次请求不带执行scope”。

若权威执行许可未知，输出应为未核实并安排补证；不得据此生成“已证实缺Grant”的审批门。若可信授权入口确认实际缺失，才走原最小差量申请。真正缺Grant的负例必须一起测，不能简单改成所有人都有权限。

### 例B：测试与候选绑定

修复X在候选甲上通过，不证明候选乙包含修复或经过验证。必须绑定精确代码/制品摘要、测试与环境、独立验收主体。不同SHA不必然失败：正式验收合同若明确允许以相同制品摘要确认，按那个合同；不能让模型自行宣布“内容应该一样”。

### 例C：环境与实际runner

能连接一个测试库，不代表runner可以创建/迁移/清理它需要的对象。能力申请要根据锁定runner的真实操作和隔离范围，不能仅看到一次CREATE错误就猜两条GRANT足够。已有授权内的准备继续；真正新增权限才按原正式路径申请。

## 7. 第一轮工程切片：不要把整篇方法交给worker自行实现

### 先做什么

复用原工程Issue与作者，先选例A这一类已经多次误判的边界。确认在当前实际版本能复现后，补“证据与结论相容”的最小自动回归及原入口修复。例B、C复用各自原在途修复，不把它们合成新的总平台。

给作者的是一个小任务包：准确仓库/分支/函数、合成输入、正式合同、必须不同的两个结果、固定测试入口及权限边界。没有合法观察工具就明确诊断能力缺口，不能靠worker猜。

### 首轮至少验证

1. 只有本次read token缺scope：不能断言主体无execute Grant。
2. 权威来源确认该主体的执行许可有效：不重复生成人工授权门；业务Case/角色/写入门仍须分别检查。
3. 权威来源确认缺Grant：保留正确拒绝并进入原授权路径，不能一律自动允许。
4. 证据属于另一个主体、资源或版本：拒绝作为本次结论依据。
5. 返回空回复、解释性FAIL或无支持结论时：不能伪报成功，也不能丢失当前补证/治理义务。

这些是预期断言，不是已有测试结果。不要为了通过它们新增全局授权查询、授予只读角色不应知道的权限信息、向生产写入试权限或读取secret。

### 再证明控制可靠性

用受控worker触发成功、无工件、FAIL、超时、旧回执、效果UNKNOWN。模型可以用替身，但正在验收的持久存储、状态转换、治理创建、结果绑定和恢复入口必须真实。故障撤除后，由正式消费者自然继续，不由测试直接调用待验的recover方法造绿。

### 最后校准真实模型

固定相同工具、权限、验收器和预算，对比：当前宽任务包、同模型窄任务包、已获准的较强模型窄任务包。报告实际任务结果、虚构blocker、错误授权申请、虚假完成、成本及人工接力，而不只比较回复是否专业。

没有模型路由许可就不自行切换；未跑写NOT_RUN。某模型局部能力未达标，不赋予它更广的流程裁判职责。

## 8. 最小性、可组合性和验证边界

五项混合了对象、关系和动作合同，不声称是五个同构算子。权限、预算、候选版本、验收器在本稿中是动作和证据合同的重要输入，而非被忽略；后续若发现它们具有不能派生的独立责任，应拆分或修订。

原语是否足够基础，需要做删除/合并实验：保持任务范围与默认能力固定，检查删掉一项后是否把同一判断偷偷移到Prompt、参数、预处理或人工身上。若以现有更小集合完成同样任务并减少总成本，候选应合并或降为派生视图，不保留固定数量。

验证状态分别记录：
- 概念整理：本稿完成；尚未独立评审其最小性/完备性。
- 案例：合成反例与预期断言；不是本稿运行的实验结果。
- 实现、集成、部署、生产业务效果、真实模型能力：本稿均不宣称已验证。
- 文档/路径检查与CI只检查仓库一致性，不能升级为上述任何运行验证。
