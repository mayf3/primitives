# 共享约定：只共享必要的连接方式

## 1. 共享什么

仓库共享四件事：可定位的 ID、来源位置、版本、显式引用。共享层不定义一种通用“人生/写作/设计对象”，也不统一各域的 `status` 或 `evidence`。

`registry.json` 列出可加载领域及组合。每个领域有独立 `module.json`、`catalog.json` 和工作文档；不需要运行服务器或安装第三方依赖。

## 2. 模块与条目

`module.json` 必须提供：`id`、`title`、`version`、`description`、`entrypoint`、`guide`、`catalog`、`depends_on`。本版三个领域的 `depends_on` 均为空。

`catalog.json` 包含 `domain` 和 `entries`。每个条目提供：`id`、`title`、`kind`、`summary`、`tags`、`path`。

- `id` 使用 `<domain>.<local-name>`，例如 `design.entry-outcome`，稳定且唯一。
- `kind` 由本领域解释：人生可以登记对象与关系，写作和设计可以登记动作；它不是公共本体枚举。
- `path` 相对领域目录，必要时用显式锚点定位小节。
- `summary` 是检索提示，详细定义以其指向的工作文档为准。
- 条目 ID 是**方法定义**的地址，不是某次用户记录的 ID。引用真实实例时另外给出其系统、原 ID、版本及位置，不把 `life.claim` 当成一条实际断言。

版本是模块独立的整合版本。本版使用 `0.1.0`；来源的 `v2`、`v1.1` 和原提交 SHA 另行保留。修文字但不改含义可升补丁版；改变适用边界或语义需要说明兼容影响。具体版本变化不触发外部项目自动更新。

## 3. 来源与新整理

每个领域的 `sources/manifest.json` 以 `imports` 列出固定快照：来源 ID、类型、仓库/上传文件、原版本或提交、导入日期、文件清单。文件清单包含领域内 `path`、原 `upstream_path`、SHA-256。

这些哈希是**导入一致性**证据：只能说明快照没有被本仓库静默改写。它们不证明原研究正确、不证明作者身份，也不把同源转述变成独立证据。

导入日期不等于原研究日期。未知日期写 `unknown`。旧会话中的 `turn…` 引用令牌不能当永久链接；保留原文，并把可解析 URL 单独登记。未打开复核的 URL 保持未复核状态。

工作文档应说明哪些是直接继承，哪些是本次整理或补写。整合时发现矛盾，保留原文并写差异说明；不能为通过校验悄悄修正快照。

## 4. 跨域连接

组合定义放在 `bridges/`。每一步注明领域、使用哪些方法 ID、输入、输出；交接注明从哪一步到哪一步、载荷和接收条件。

允许的组合关系为：`uses`（使用方法）、`informs`（提供判断输入）、`derived_from`（派生于材料）、`evaluates`（针对指定对象进行检查）。这些词只描述组合，不自动写入任何领域的数据关系。

禁止从连接推导等价：

- 一次 Activity `uses` 一个设计原语，不表示两者是同类对象。
- 成稿 `derived_from` 一份材料，不表示所有新增解释都来自材料。
- 页面测试 `evaluates` 一项设计假设，不表示它支持所有相关人生判断。

组合的机器记录锁定 `module_versions`。升级某领域后，复核受影响组合再更新所锁版本，不能自动接受状态映射。

## 5. 各域验证分别进行

人生保留其事实/判断与本人确认规则。写作保留建议、采用、应用、指定范围检查的差别。设计分开维护来源核对、实施状态、用户验证状态。共享层不提供一个覆盖三者的 `verified: true`。

本仓库工具检查 JSON、ID、路径、来源哈希、模块隔离、组合引用，以及设计案例的状态枚举。它不确认人生记录，不评判文学质量，不证明 WCAG 合规，也不模拟真实用户结果。

## 6. 增加新领域

创建自己的 `domains/<id>/`，写独立使用指南及领域定义，提供模块和条目索引，记录来源，再加入 `registry.json`。只有真实需要协作时才新增组合。不要为了占位先发明视频、DIY 等领域的原语内容。
